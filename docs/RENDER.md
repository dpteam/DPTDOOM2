# Режим рендера: кадры для видео

`-render <каталог>` — это не скриншот, а **съёмка**: движок проходит игру без окна и пишет
каждый кадр отдельным PNG с фиксированной частотой. Кадры собираются в видео любым
инструментом — `ffmpeg`, монтажкой, композитором.

Нужно это для машинимы и «песочницы»: когда игру крутит не игрок, а сценарий, и от неё нужен
материал, а не геймплей.

```powershell
# 10 секунд обычной игры в mp4
powershell -NoProfile -File tools\render-video.ps1 -Out clip.mp4 -Tics 350 -Skip 35

# только оружие, с прозрачностью, для композитинга
powershell -NoProfile -File tools\render-video.ps1 -Out gun.mov -Layer weapon -Key alpha -Tics 140

# кадры без кодирования: собрать самому
powershell -NoProfile -File tools\render-video.ps1 -Out frames -FramesOnly -Tics 350
```

Без скрипта, напрямую:

```powershell
dptdoom.exe -render frames -iwad doom2.wad -warp 1 -skill 3 -tics 350 -renderskip 35
ffmpeg -framerate 35 -i frames\frame_%05d.png -c:v libx264 -crf 18 -pix_fmt yuv420p clip.mp4
```

## Ключи

| Ключ | По умолчанию | Что делает |
|---|---|---|
| `-render <каталог>` | — | пишет `frame_00000.png`, `frame_00001.png`, … и `render.txt` |
| `-renderfps N` | 1 | кадров на тик: 1 → 35 fps, 2 → 70, 3 → 105 |
| `-renderres N` | 1 | множитель над 320×200: 1 → 320×200, 2 → 640×400, 3 → 960×600 |
| `-renderskip N` | 0 | сколько тиков просимулировать до начала записи |
| `-tics N` | без предела | на каком тике остановиться |
| `-renderlayer full\|world\|weapon\|hud` | full | что рисовать в кадре |
| `-renderkey green\|alpha` | green | чем заполнить пустое место слоя |
| `-grade night\|noir\|sepia\|vivid` | нет | именованный цветовой грейд |
| `-saturation X` | 1 | насыщенность: 0 — серый, 1.3 — сочнее |
| `-tint R,G,B` | 1,1,1 | множители каналов, например `1.1,0.95,0.8` |
| `-brightness X` | 0 | прибавка к каждому каналу, −1…1 |
| `-contrast X` | 1 | контраст вокруг середины |
| `-posterise N` | 0 | уровней на канал, 4 — жёсткий постер |
| `-pitch N` | 0 | наклон камеры в пикселях (работает и без окна) |
| `-yaw N` | 0 | поворот камеры в градусах, **не** поворот актора |

`-render` включает headless сам: окно и показ кадра тут не нужны, а зависимость от машины —
вредна.

## Детерминизм: почему съёмку можно повторить

Три правила, и каждое появилось из конкретной поломки:

1. **Частота фиксирована.** Пейсер двигается идеальным шагом кадра, а не измеренным временем,
   поэтому кадр N всегда попадает в одну и ту же дробь одного и того же тика. Симуляция при
   этом идёт свои 35 тиков в секунду, и кадр, накрывающий больше одного тика, прогоняет их все.
2. **`-renderskip` обязателен на практике.** Заставка начала уровня сеет высоты столбцов из
   часов, поэтому занимает переменное число обновлений: запись с нулевого кадра не повторяется
   и начинается на чёрном экране.
3. **В конце печатается хеш мира** строкой `State: mobj=… sector=… tic=…`, как в обычном
   headless-прогоне. Две съёмки одной команды обязаны дать один хеш; если нет — это уже не
   «другая картинка», а другой мир.

```powershell
# один и тот же кадр-мир дважды
dptdoom.exe -render a -tics 70 -renderskip 35 -iwad doom2.wad -warp 1 | Select-String State
dptdoom.exe -render b -tics 70 -renderskip 35 -iwad doom2.wad -warp 1 | Select-String State
```

## Слои: `world`, `weapon`, `hud`

Кадр можно разложить на слои и собрать заново уже в монтажке:

| Слой | Что в кадре | Зачем |
|---|---|---|
| `full` | всё, как в игре | готовый материал |
| `world` | уровень без оружия и без HUD | подложка, на которую кладут свой HUD или чужое оружие |
| `weapon` | только оружие | настоящее оружие Doom поверх другого кадра |
| `hud` | статус-бар, чат, строка сообщений | HUD переживает перекадрирование и не растягивается |

Пустое место слоя заполняется по `-renderkey`:

- `green` (по умолчанию) — чистый зелёный `0,255,0`. Такого цвета нет в палитре Doom, поэтому
  хромакей убирает его чисто, а ключ есть в любом редакторе;
- `alpha` — настоящая прозрачность (RGBA PNG). Лучший вариант там, где поддерживается: нет
  ореола по краям и нечего вычитать.

```powershell
# оружие с альфой поверх своего фона
ffmpeg -i background.mp4 -i gun.mov -filter_complex "[0:v][1:v]overlay" out.mp4
```

Слои рисуются **теми же проходами**, что и обычный кадр: `hud` — тот же статус-бар и та же
строка сообщений, поэтому собранный кадр совпадает с плоским.

## Цвет: грейд — это палитра, а не кадр

Движок рисует индексами палитры и переводит их в цвет один раз за кадр. Грейд правит **256
записей палитры**, поэтому:

- стоит 256 операций на кадр, а не по операции на пиксель;
- **не меняет мир**: симуляция цвета не видит, хеш мира остаётся тем же (это проверяет
  `tools/test-render.ps1`);
- применяется к той палитре, что использует кадр, — то есть вспышка урона в моде тоже
  окрашивается, а не выпадает из общего вида.

Порядок операций зафиксирован, чтобы две съёмки совпадали: насыщенность → оттенок →
контраст → яркость → постеризация.

Именованные грейды — отправные точки, отдельные ключи их донастраивают:

| Имя | Что получается |
|---|---|
| `night` | темнее, холоднее, приглушённая насыщенность |
| `noir` | чёрно-белое с высоким контрастом |
| `sepia` | старая плёнка |
| `vivid` | сочнее и контрастнее, для превью |

```powershell
# ночь, но без постеризации и с более тёплым оттенком
dptdoom.exe -render night -grade night -tint 1.1,1.0,0.9 -iwad doom2.wad -warp 1 -tics 350
```

## Камера: `-pitch` и `-yaw`

Оба — **подача, а не состояние игры**: ни в командах тика, ни в демо, ни в хеше мира. Актор
продолжает смотреть и стрелять туда, куда велит ввод, а картинка смотрит в другом направлении.

- `-yaw N` поворачивает камеру в градусах. Снимать «со стороны» можно, не разворачивая игрока;
- `-pitch N` наклоняет вид (скос проекции, как в Duke Nukem 3D), предел ±70 пикселей.

> **Исправлено по дороге:** в headless-прогоне `-pitch` не работал вообще. `UpdateViewPitch`
> обнулял наклон, когда у движка нет мыши, — это правильно для окна, потерявшего ввод, и
> неправильно для камеры, выставленной нарочно. Теперь без устройства ввода берётся значение с
> командной строки.

## Рецепты

```powershell
# 9:16 для Reels: рендер в 2×, потом кадрирование
powershell -NoProfile -File tools\render-video.ps1 -Out wide.mp4 -Tics 350 -Res 2
ffmpeg -i wide.mp4 -vf "crop=ih*9/16:ih,scale=1080:1920" -c:v libx264 -crf 18 reel.mp4

# немое кино: noir + постеризация
powershell -NoProfile -File tools\render-video.ps1 -Out silent.mp4 -Tics 350 -Grade noir

# GIF-зацикливание
ffmpeg -framerate 35 -i frames\frame_%05d.png -vf "fps=15,scale=320:-1:flags=neighbor" -loop 0 loop.gif

# замедление вдвое без пересчёта кадров
ffmpeg -i clip.mp4 -vf "setpts=2.0*PTS" -an slow.mp4

# HUD отдельно, чтобы положить поверх своего кадра
powershell -NoProfile -File tools\render-video.ps1 -Out hud.mov -Layer hud -Key alpha -Tics 350
```

## Вместе с ffmpeg-skill

Режим отдаёт ровно то, что ждёт `sequence.py`: нумерованные PNG и `render.txt` с частотой и
размером. Ничего не нужно угадывать:

```text
# кадры
python3 $S/sequence.py frames/frame_%05d.png -o take.mp4 --fps 35

# что получилось — посмотреть контактным листом
python3 $S/look.py take.mp4 --sheet sheet.png

# соответствие площадке
python3 $S/check.py take.mp4 --platform reels
```

`render.txt`:

```text
frames = 315
fps = 35
width = 640
height = 400
pattern = frame_%05d.png
layer = Full
pitch = 0
yaw = 25
grade = saturation 0.75, tint 0.75/0.85/1.25, brightness -0.12, contrast 1.15
```

Этот файл читается и глазами, и скриптом; он же фиксирует, **чем** снят кадр, чтобы через
неделю не гадать, откуда взялся оттенок.

## Чего пока нет

Честно, потому что иначе это ищут и не находят:

- **звука нет.** Рендер пишет только картинку: звук игры не записывается. Музыку и эффекты
  добавляет монтаж. Отдельные звуки можно отрендерить в WAV через `-soundtest`;
- **камера стоит на игроке.** `-yaw`/`-pitch` меняют направление и наклон, но не положение:
  свободной камеры, полёта по пути и ключевых кадров нет;
- **нет отдельного слоя спрайтов.** `world` — это весь уровень целиком; вырезать из него
  монстров для композитинга нельзя;
- **управление — только демо или бот.** Ввод в headless не читается, поэтому «сценарий» — это
  `-playdemo`, `-bots`/`-botinput` или заранее записанная демка.

## Куда развивать

Ближайшее, что даст больше всего свободы машиниме:

1. **Путь камеры**: ключевые кадры `время, x, y, z, yaw, pitch` из файла и интерполяция между
   ними — облёты, проезды, «камера отъезжает». Технически это те же `viewX/viewY/viewZ/viewAngle`,
   что уже есть, только берутся из файла, а не у игрока.
2. **Свободная камера**: положение отдельно от игрока, чтобы снимать сцену, в которой игрока нет
   в кадре.
3. **Слой спрайтов** отдельно от стен: тогда монстров можно класть на другой фон.
4. **Управление временем**: пауза на кадре, замедление внутри съёмки, а не в монтаже.
5. **Звук в рендере**: писать WAV рядом с кадрами, чтобы эффекты совпадали с картинкой по тикам.
