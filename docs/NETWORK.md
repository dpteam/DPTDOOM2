# Сеть

Кооператив построен на **lockstep**: все участники симулируют одни и те же тики
с одними и теми же командами. Состояние мира не передаётся вообще — только
`TicCmd` (вперёд/вбок/поворот/кнопки). Это возможно, потому что движок
демо-совместим и детерминирован.

## Запуск

```powershell
# хост: ждёт игрока, затем стартует
dptdoom.exe -iwad doom2.wad -net host -players 2 -port 5029 -warp 1 -skill 3

# гость
dptdoom.exe -iwad doom2.wad -net join -address 192.168.1.10:5029
```

Адрес можно задать как `host:port` — тогда `-port` не нужен.

Без проброса порта — через relay (подробности в `docs/RELAY.md`):

```powershell
# хост: публикуется на master и открывает relay-канал
dptdoom.exe -iwad doom2.wad -net host -players 2 -master play.dartpower.xyz:25135 -relay

# гость: id сессии печатает хост
dptdoom.exe -iwad doom2.wad -net join -relay-master play.dartpower.xyz:25135 -relay-session <id>
```

## Порты

| Что | Порт | Протокол | Где открывать |
|---|---|---|---|
| Игровой хост | **5029** | TCP | у хоста (у кого запущен `-net host`) |
| Master server | **25135** | TCP | только на машине с `dptdoom-master.exe` |
| Master relay | **25136** | TCP | там же, где master, если включён `--relay` |

Гостю открывать ничего не нужно: он сам подключается наружу, а ответ приходит по
уже установленному соединению.

**С relay хост тоже ничего не открывает.** Он подключается наружу к master, и
проброс порта 5029 ему не нужен — см. `docs/RELAY.md`.

Порт игры по умолчанию — `NetProtocol.DefaultPort`, порт master —
`MasterProtocol.DefaultPort`, relay — порт master + 1. Все три можно сменить:
`-port` у игры, `--port` и `--relay-port` у master.

## Файрвол

Windows по умолчанию блокирует входящие подключения, поэтому хост без правила в
файрволе ждёт игрока, которого никто не может достичь. Есть скрипт:

```powershell
# посмотреть, что будет сделано, ничего не меняя
powershell -NoProfile -File tools/firewall.ps1 -WhatIf

# открыть игровой порт (обычный случай)
powershell -NoProfile -File tools/firewall.ps1

# дополнительно открыть порт master (на машине, где он запущен)
powershell -NoProfile -File tools/firewall.ps1 -IncludeMaster

# убрать правила
powershell -NoProfile -File tools/firewall.ps1 -Remove
```

Запускать **от имени администратора**. Без прав скрипт ничего не меняет, а
печатает готовую команду для повторного запуска.

`-IncludeMaster` открывает два порта: каталог (25135) и relay (25136). Второй
нужен только если master запущен с `--relay`: без него хост опубликуется в
списке, но подключиться к нему никто не сможет.

То же самое вручную, одной строкой:

```powershell
# Windows 8 / Server 2012 и новее
New-NetFirewallRule -DisplayName "DPT.DOOM game host (TCP 5029)" `
  -Direction Inbound -Action Allow -Protocol TCP -LocalPort 5029 -Profile Any

# Windows 7 и старше, включая XP
netsh advfirewall firewall add rule name="DPT.DOOM game host (TCP 5029)" `
  dir=in action=allow protocol=TCP localport=5029

# Windows XP / Server 2003 (у них нет advfirewall)
netsh firewall add portopening TCP 5029 "DPT.DOOM"
```

Скрипт сам выбирает нужный вариант: на XP и Server 2003 `New-NetFirewallRule`
не существует, и там используется `netsh firewall`. Это не украшательство — XP
целевая платформа порта.

Кроме порта, скрипт добавляет правило для самой программы
(`dptdoom.exe`). Оно нужно, если порт меняли через `-port`: правило на порт тогда
не совпадёт, а правило на программу совпадёт.

## Проброс портов на роутере

Файрвол — только половина. Если хост за роутером, входящее подключение из
интернета до него не дойдёт, пока роутер не перешлёт порт на эту машину.

1. Узнать локальный адрес машины: `ipconfig`, строка `IPv4-адрес`
   (обычно `192.168.х.х`).
2. В веб-интерфейсе роутера найти раздел **Port Forwarding** /
   **Virtual Server** / **Проброс портов**.
3. Правило: внешний порт **5029**, внутренний **5029**, протокол **TCP**,
   адрес — локальный адрес из шага 1.
4. Внешний адрес узнать на сайте роутера или через `Invoke-RestMethod ifconfig.me`.
5. Гость подключается по внешнему адресу: `-address <внешний ip>:5029`.

Если внешний адрес меняется (обычный домашний интернет), нужен статический IP
или DDNS.

**Relay через master работает и не требует проброса.** Если master запущен с
`--relay`, хост может играть вообще без проброса порта и без правила в файрволе:
обе стороны подключаются наружу к master, а он соединяет потоки. То же снимает
проблему NAT hairpin (два игрока за одним роутером). Подробности и командная
строка — `docs/RELAY.md`.

Без relay и без проброса остаётся только VPN (Radmin, Hamachi, ZeroTier,
WireGuard): он даёт обеим машинам адреса в одной виртуальной сети, и тогда
проброс не нужен.

### UPnP: попросить роутер пробросить самому

Вместо шагов 1–3 выше можно попросить роутер сделать это по UPnP:

```powershell
dptdoom.exe -iwad doom2.wad -net host -players 2 -upnp
```

Хост сам находит шлюз, добавляет правило (внешний порт = внутренний = `-port`,
протокол TCP) и печатает адрес, который осталось сообщить товарищу:

```
Net: port 5029 forwarded over UPnP; friends can reach 203.0.113.7:5029.
Net: HOSTING (PORT 5029; PLAYERS 2; WAITING FOR PLAYER 0/1; UPnP: 203.0.113.7:5029)
```

Правило **снимается** при выходе из игры: проброс, который никто не убрал, живёт в
таблице роутера до перезагрузки, то есть порт открыт в интернет и через неделю
после игры.

Флаг **явный**, а не автоматический: программа, которая молча открывает порт в
интернет при первом запуске, не спрашивала разрешения.

Что бывает вместо успеха, и всё это не ошибка игры:

| Ответ | Что значит |
|---|---|
| `UPnP: 203.0.113.7:5029` | проброс есть, этот адрес давать товарищу |
| `UPnP: FORWARDED` | проброс есть, но роутер не сообщил внешний адрес |
| `UPnP: NOT FORWARDED` + причина в консоли | шлюза нет, UPnP выключен, порт занят другим правилом |

Частые причины в консоли: «no router answered UPnP» (UPnP выключен в роутере или
сеть его не пропускает), «another program already forwards this port» (осталось
правило от прошлого запуска — UPnP error 718), «this router does not support port
forwarding over UPnP» (501).

Три ограничения, о которых честнее сказать сразу:

- **Двойной NAT у провайдера.** Роутер пробросит порт на себя, но его собственный
  «внешний» адрес — внутренний адрес провайдера. Тогда внешний адрес будет из
  диапазона `10.`/`100.64.`/`192.168.`, и снаружи он недоступен: нужен проброс на
  стороне провайдера или relay.
- **Роутеры без UPnP** (часть прошивок, корпоративные сети, гостевые Wi-Fi) —
  проброс руками или relay.
- **Порт, занятый другим правилом**, не перезаписывается: роутер отвечает ошибкой
  718, и игра об этом говорит. Взять другой порт — `-port`.

Проверка: `UpnpProtocolTest` (25, разбор SSDP и SOAP без сети) и
`tools/test-upnp.ps1` (живой запуск: без флага UPnP не трогается, с флагом хост
доходит до `HOSTING` за ограниченное время и честно сообщает результат).

## Проверка, что порт действительно открыт

```powershell
# слушает ли игра порт (должна быть строка LISTENING)
netstat -ano | Select-String ':5029'

# виден ли порт снаружи (запускать на другой машине, не на хосте)
Test-NetConnection -ComputerName <внешний ip> -Port 5029
```

Если `netstat` показывает `127.0.0.1:5029`, а не `0.0.0.0:5029`, игра слушает
только локально. Хост обязан слушать `0.0.0.0` — это `TcpListener(IPAddress.Any, port)`
в `NetSession.OpenListener`.

## Протокол

Игровой протокол **v1**, отдельный от directory-протокола master. Кадр:

```
"DPTN" | version u16 | type u16 | payload length u32 | payload
```

| Type | Имя | Payload |
|---|---|---|
| 1 | HELLO | имя игрока |
| 2 | WELCOME | индекс игрока, размер сессии, настройки, имена |
| 3 | REJECT | причина |
| 4 | TIC | номер тика u32, игрок u8, forward, side, angle u16, buttons |
| 5 | BYE | — |
| 6/7 | PING/PONG | — |

Настройки сессии (карта, сложность, режим, правила, digest WAD) фиксирует хост и
присылает в WELCOME. Гость сверяет digest своих WAD с хостовым и отказывается
стартовать при расхождении — иначе мир разъедется на первом же тике.

## Порядок тика

```
1. локальный TicCmd собран из ввода
2. он отправлен сразу (иначе первый тик ждал бы сам себя)
3. ждём TIC всех остальных игроков на этот номер
4. как только все есть — применяем и обновляем мир
5. tic++
```

Пока команда не пришла, мир стоит на месте: это честное ожидание, а не
замедление. Локальный ввод ограничен очередью в 4 команды, чтобы при подвисании
пира управление не уезжало на секунды вперёд.

## Задержка и скорость симуляции

Кооператив построен на lockstep, и это накладывает ограничение, которое важно
понимать, потому что оно выглядит как «лагает сеть», хотя сеть тут ни при чём.

Тик нельзя симулировать, пока не пришла команда напарника на этот же тик. А
напарник формирует её, когда сам дойдёт до этого тика. Если команды отправлять
ровно в тот момент, когда они нужны, получается **один тик на один round-trip**:

| Пинг | Тиков/с без упреждения | Нужно игре |
|---|---:|---:|
| LAN | 87 | 35 |
| 100 мс (Россия ↔ Литва) | **17.5** | 35 |
| 200 мс | 9 | 35 |

То есть при 100 мс мир шёл **вдвое медленнее** обычного: оружие стреляло реже,
двери ехали медленнее, всё ощущалось «тормознутым». Трафик при этом был ни при
чём: сессия на 700 тиков занимает около 31 КБ, это 44 байта на тик и примерно
1.5 КБ/с на двоих — 0.0015% канала в 800 Мбит/с.

Поэтому ввод отправляется **на `Delay` тиков вперёд**: к моменту симуляции тика
N команда напарника на N была отправлена уже давно. Плата — те же `Delay` тиков
задержки ввода, и это обычный компромисс любой lockstep-игры.

`Delay` измеряется при подключении (семь ping/pong до приветствия, берётся
**медиана**, а не среднее) и передаётся гостю **внутри приветствия**: обе стороны
обязаны взять одно и то же число. Причина не в нумерации тиков — она от `Delay`
не зависит, — а в темпе: мир идёт со скоростью **наименьшего** буфера в сессии.
Гость, который держит в руке одну команду, тормозит хоста до «тик на round-trip»
при любом размере хозяйского буфера. Один распорядитель, одно число — иначе самый
медленный участник молча задаёт скорость всем.

Формула: `ceil(round-trip / 28.5 мс) + запас на джиттер`, в пределах 0..10, и 0 на
LAN.

Запас на джиттер считается по **медианному абсолютному отклонению**, а не по
размаху. Размах семи замеров решается одним самым неудачным замером: один провал
на 40 мс на чистом канале покупал лишний тик задержки навсегда. MAD такой провал
игнорирует, а на канале, который действительно дрожит, растёт вместе с ним —
поэтому запас получается ступенчатым (0..2 тика), а не «да/нет». Проверка —
`DelayPolicyTest`.

Редкий провал на сотни миллисекунд этим не покрывается сознательно: платить
постоянные четыре тика за то, что раз в минуту бывает рывок, — это цена, которую
платит каждый игрок в каждой чистой сессии. Такой рывок **поднимает** буфер задним
числом (`DelayPolicy.Adjust`), и это дешевле.

После этой правки при 100 мс пинга сессия идёт **57 тиков/с** вместо 17.5, при
200 мс — 49.6. Оба случая проверяет `tools/test-net-latency.ps1`, который
подделывает задержку через `tools/latency-proxy.ps1` и падает, если скорость
снова окажется привязана к round-trip. Скрипт гоняет и канал с джиттером
(50 мс в одну сторону, ±30 мс): на нём запас и проверяется.

### Подстройка на ходу

Буфер, измеренный при подключении, врёт в одну сторону: семь замеров до начала
трафика показывают канал **до** нагрузки. На живом замере 100 мс в одну сторону
под нагрузкой латентность вырастала с 254 до 390 мс, и замер при подключении
занижал нужду на треть.

Поэтому хост раз в две секунды пересматривает размер:

| Что случилось | Что делает буфер |
|---|---|
| ≥ 5% тиков окна ждали напарника дольше тика | растёт: сразу до измеренной нужды, иначе на тик, но не выше «измеренная нужда + 2» |
| застоев мало или нет | тик отдаётся назад, но не ниже измеренной нужды и только после 60 с тишины |

Меняется не больше чем на тик за окно, а назад — только после минуты тишины.
Это и есть сглаживание: изменение на 28 мс игрок не чувствует как рывок, а буфер
подползает к верному значению, а не прыгает.

**Ждать меньше тика — не застой.** Пейсер кадра съедает ожидание короче тика, тик
укладывается в свой бюджет, игрок ничего не видит. Если считать и такие ожидания,
идеально гладкая сессия на loopback читается как «50% тиков в застое», а буфер
ползёт к максимуму на ровном месте — это ловушка, на которую я наступил, прежде
чем появился `DelayPolicy.IsFelt`.

**Один опоздавший тик — не нехватка буфера.** Он означает, что на мгновение
задумалась машина, а не канал: платить за это постоянным тиком задержки ввода
плохо, и отдать его назад будет некому. Поэтому рост включает **доля** опаздавших
в окне (5%), а не факт. Доля, а не число: окно — это две секунды «как быстро идёт
игра», 70 тиков в оконной игре и несколько сотен в headless-прогоне, и фиксированное
число значило бы в них разное.

**Рост ограничен сверху.** Потолок — измеренная нужда плюс два тика. Без него
буфер уползал в максимум и оставался там: на канале с джиттером какая-то доля
пакетов опаздывает всегда, так что «расти, пока есть застои» не имеет точки
остановки, которую канал способен достичь. Два тика сверху — это запас на то, что
замер при подключении оптимистичен (он делается до появления трафика самой сессии);
дальше джиттер канала сильнее любого буфера, и лишняя задержка ввода уже ничем не
окупается. Это вторая ловушка того же рода, что и первая, и обе найдены замером.

Гость применяет чужое решение из кадра `TypeDelay` и никогда не принимает своё;
хост кадр `TypeDelay` игнорирует. `-netdelay` отключает подстройку целиком: он
означает «не угадывать», и тест, попросивший 3 тика, должен получить 3 тика.

Замер на нагрузке через прокси (50 мс в одну сторону, ±30 мс джиттера, 700 тиков,
буфер задан вручную, чтобы видеть только его влияние):

| Буфер | тиков/с | тиков в застое |
|---|---|---|
| 4 тика (114 мс) | 39.5 | 36.3% |
| 6 тиков (171 мс) | 62.2 | 21.9% |
| 8 тиков (228 мс) | 79.7 | 16.9% |
| 10 тиков (285 мс) | 87.3 | 15.1% |

Остаток в 15% на последней строке — это джиттер самого прокси, а не нехватка
буфера: он задерживает каждый пакет на 20..80 мс, а lockstep ждёт самый поздний из
пачки. Поэтому цель «ноль застоев» недостижима, и решение принимается по скорости
мира, а не по их числу. При 100 мс в одну сторону без джиттера буфер поднимается
сам с 6 до 10 за три окна и даёт 55 тиков/с против 26 при ручных 3.

Принудительно задать значение можно ключом `-netdelay <0..10>` у хоста:

```powershell
# 5 тиков упреждения, около 143 мс запаса
dptdoom.exe -iwad doom2.wad -net host -players 2 -netdelay 5
```

Больше 10 тиков не даёт: 286 мс — это уже игра вслепую, а не компенсация.

## Пароль сессии

```powershell
# хост: пускать только своих
dptdoom.exe -iwad doom2.wad -net host -players 2 -password "наши-в-субботу"

# гость: тот же пароль
dptdoom.exe -iwad doom2.wad -net join -address 192.168.0.5:5029 -password "наши-в-субботу"
```

Пароль ложится в необязательный хвост `HELLO` (отдельный бит во флаговом байте) и
сверяется хостом **до** `WELCOME`, то есть до выдачи слота. Неверный — отказ с
причиной:

```
Net: CONNECTION FAILED (127.0.0.1:7100 REFUSED: WRONG PASSWORD)
Net: CONNECTION FAILED (127.0.0.1:7100 REFUSED: THIS SESSION NEEDS A PASSWORD)
```

Отказ — это **ответ, а не сбой** (`NetRefusalException`), поэтому переподключение
не пытается снова: повторять нечего, пароль от этого не изменится.

**Что пароль делает и чего не делает.** Он не пускает случайных людей в игру для
друзей. Он **не** шифрует трафик: сам пароль идёт открытым текстом в рукопожатии,
а relay — вообще прозрачная труба через master. Кто видит поток, тот видит и
пароль, и игру. Не выдавать его за защиту канала — ни в UI, ни в документации,
иначе кто-нибудь на неё понадеется.

Что сделано для того, чтобы он хотя бы не подбирался по времени ответа: сравнение
идёт не побайтово с выходом на первом различии (это даёт один символ за замер), а
по двум хешам фиксированной длины, без досрочного выхода — время не зависит ни от
того, где строки разошлись, ни от длины догадки. Проверка — `ServerPasswordTest`.

Три вещи, которые сознательно устроены именно так:

- **пароля нет в `SessionSettings`.** Настройки едут в приветствии и публикуются
  мастеру для списка серверов; пароль не должен попадать ни туда, ни в логи, ни в
  отчёт `netstats`;
- **пароля нет и на экране.** Статус хоста печатает `PASSWORD ON`, а не значение:
  экран photographed для отчётов об ошибках, и `dmesg`-лог перенаправляют в файлы
  почти все скрипты;
- **возврат по токену пароль не спрашивает.** Токен — доказательство, что слот
  выдавали именно этому игроку; спрашивать снова значило бы выкидывать из игры
  всех, кто в ней уже есть, если хост сменил пароль.

Старая сборка без пароля в защищённую сессию не попадёт — и получит внятное
«this session needs a password», а не «ожидался hello».

Ещё одно ограничение, о котором честнее сказать сразу: пароль стоит в командной
строке процесса, а её видно другим пользователям той же машины через WMI. На своей
машине это не важно, на общей — важно. Убрать это можно только передачей пароля не
через аргументы (файл, `stdin`, переменная окружения), и это отдельная работа, а не
побочный эффект нынешней.

## Банлист и лог подключений

```powershell
dptdoom.exe -iwad doom2.wad -net host -players 4 `
            -bans "bans.txt" -netlog "net.log"
```

Файл правил — тот же формат, что у мастера, плюс правила по нику. Один формат на
оба случая, чтобы оператору не приходилось учить второй диалект:

```
# до конца строки — комментарий
203.0.113.7                  один адрес
203.0.113.0/24               подсеть
203.0.113.7 until 2026-01-01T00:00:00Z    временный бан
2001:db8::/32                IPv6 тоже работает
name troll                   ник целиком
name bad*                    ник по маске, * в любом месте
name bad* until 2026-01-01T00:00:00Z
```

Без `-bans` берётся `dptdoom-bans.txt` из каталога данных — **если он существует**.
Явно названный файл, которого нет, это ошибка, а не «банов нет»: иначе опечатка в
пути тихо оставляет сессию открытой, пока хост уверен в обратном.

Правила проверяются **до** выдачи слота, и ник — сразу после `HELLO`, потому что
раньше его просто не существует. Бан по адресу тоже проверяется после `HELLO`, и
это осознанный размен: если закрыть сокет, не прочитав кадр, ядро отправит сброс, и
гость увидит «connection reset by peer» вместо «banned». А именно «сказать, что
забанен» — весь смысл банлиста.

Забаненный не может и вернуться по токену: проверка стоит перед ветвью возврата.
Бан, который не действует на того, кто уже в игре, — не бан.

**Лог** пишется по строке на событие, с меткой UTC:

```
2026-10-24T19:39:07Z join name="guest" address=127.0.0.1 player=2
2026-10-24T19:39:16Z leave name="guest" address=127.0.0.1 player=2 reason=quit
2026-10-24T19:39:21Z resume name="guest" address=127.0.0.1 player=2
2026-10-24T19:40:02Z refuse name="troll" address=203.0.113.9 reason=banned: name troll*
```

**Причина в строке ухода — это и есть смысл строки.** `leave` без неё не отличает
игрока, который вышел сам, от того, у кого умер роутер, и от того, на кого махнули
рукой. Три разные вещи для разбора.

Ник заключается в кавычки, а кавычка, обратный слэш и перевод строки экранируются:
ник — это текст от игрока, который попадает в файл, и неэкранированный перевод
строки подделывает лишнюю запись в логе.

Файл ротируется на 1 МБ в `.1`, старая `.1` удаляется. Пароля в логе нет никогда.

**Чего лог на хосте не может.** В режиме relay хост видит адрес мастера, а не
игрока: `address=-`. Бан по адресу там неприменим — это не «не сработал», а «не
знает», и честнее так и написать, чем банить мастера и отрезать всех сразу. Для
relay остаются пароль и бан по нику.

## Что сессия о себе рассказывает

`netstats` в консоли (`~`) и итоговая сводка в лог при выходе. Числа одни и те же,
чтобы жалобу игрока и вывод теста можно было сравнивать построчно:

```
role host direct, player 1 of 2, players connected 2
ping 201 ms, jitter 23 ms, input delay 9 tics = 257 ms (changed 3 times)
tics 900, rate 81.8 of 35, wall 17 s
stalls 166 totalling 9250 ms, 18.4% of tics, reconnects 0
```

- **jitter** — рядом с пингом, потому что «лагает, а пинг нормальный» иначе
  необъяснимо: чистые 40 мс и 40 мс, которые гуляют на ±120, на одном пинге
  выглядят одинаково.
- **input delay … (changed N times)** — сколько раз буфер подстраивался сам.
- **rate** — сколько тиков в секунду сессия **фактически** шла, а не сколько
  просила. Сессия, треть жизни ждавшая напарника, действительно шла в две трети
  скорости, и скрывать это — то же самое, что не отвечать на «почему лагает».
- **stalls** — тики, которые ждали напарника дольше тика. Единственный показатель,
  который говорит, что буфер был мал, а не что канал медленный.
- **reconnects** — счётчик переподключений, тот же, что у `NetReconnectCount`.

В сети это **вывод по запросу**, а не поток: строки с подстройкой буфера
печатаются только при изменении, чтобы лог не превращался в шум.

## Правила кооператива

Три правила меняют **симуляцию**, поэтому их выбирает хост и они приезжают гостю
внутри приветствия. Задать их на стороне гостя нельзя: разные значения дали бы
разные миры и рассинхрон на первом же тике.

| Правило | По умолчанию в коопе | Ключ |
|---|---|---|
| Игроки проходят друг сквозь друга | выкл (вкл при 4+ игроках) | `-noblock` |
| Дубли оружия с дезматч-карт | не спавнятся | `-coopweapons` |
| Ключи общие на команду | вкл | `-nosharedkeys` |

**Проход сквозь друга.** Doom всегда позволял игрокам блокировать друг друга. На
двоих это игра; на четверых это пробка в каждом проёме, а последний ещё и
выдавливается из лифта. Правило узкое: только игрок против игрока и только вне
дезматча — монстры, бочки и геометрия карты блокируют как обычно.

**Дубли оружия.** WAD не умеет сказать «эта плазма стоит здесь для дезматча». Зато
умеет сказать, что одна и та же пушка поставлена несколько раз, — а это ровно и
есть те дубли: на дезматч-карте дробовик лежит в четырёх местах, чтобы он всегда был
под рукой. Поэтому правило оставляет **первую** копию каждой пушки в порядке карты,
остальные не спавнятся. Порядок карты фиксирован, так что мир на обеих сторонах
получается одинаковым. В одиночной игре правило не действует вообще — там спавнится
всё, как и раньше.

**Общие ключи.** Ванильный Doom и в сети оставляет ключ на месте, так что второй
игрок может подойти и взять его сам. Это работает, пока он рядом, и ломается, как
только первый ушёл с ключом за дверь. Поэтому ключ сразу получает вся команда. Сам
ключ при этом не исчезает: через дверь проходит каждый.

## Чат

`T` открывает строку ввода, `Enter` отправляет, `Esc` отменяет, `Backspace`
стирает. Сообщение показывается в строке сообщений (той же, что и подбор
предметов) и висит 8 секунд.

Чат **не является состоянием игры**: он не входит ни в тик, ни в демо, ни в
сохранение, ни в хеш мира. Иначе два игрока, печатающие друг другу, могли бы
рассинхронизировать lockstep — то есть болтовня ломала бы игру.

Гость видит только хост, поэтому сообщение гостя пересылает хост: без этого в
сессии на трёх игроков двое никогда не увидят друг друга. Свой текст показывается
локально, а не возвращается по сети — иначе у хоста, который и отправитель, и
транслятор, каждая строка появлялась бы дважды.

Пока идёт ввод, ввод игры **подавлен** (`IUserInput.Suppressed`): движение читается
из состояния клавиш, а не из событий, поэтому набор `wasd` уводил бы игрока с
места. Заодно это не даёт набрать чит в чат и получить его эффект.

Длина ограничена 96 символами: в `Chat` — чтобы игрок видел предел, и в кадре —
чтобы руками собранный пакет не был длиннее.

Проверки: `ChatTest` (строка ввода, 8 проверок) и `NetChatTest` (транспорт, 5
проверок, включая пересылку между двумя гостями).

## Боты в сетевой игре

Ботов можно добавить хосту: `-net host -players 4 -coopbots 2`. `-players` —
общее число слотов, включая ботов.

Ботов водит **только хост**, и это не ограничение, а способ не разойтись:
команда бота уходит по сети как команда игрока, гость её просто получает. Если бы
боты считались на обеих сторонах, любая разница в их логике или во времени
развалила бы lockstep.

Боты занимают **последние** слоты, поэтому первый гость всегда попадает на слот
сразу после хоста, а не на слот, которым уже управляет бот. Хост ждёт людей, а не
ботов: `-players 4 -coopbots 2` означает «хост плюс один гость», и ожидание
заканчивается, когда приходит гость.

Проверка: `tools/test-net-bots.ps1` — прогоняет 3 слота с 1 ботом и 4 слота с 2
ботами, и требует совпадения хешей мира у хоста и гостя.

## Обрыв связи и возврат

Соединение может умереть молча: Wi-Fi отвалился, роутер сбросил NAT-таблицу,
провайдер моргнул — при этом FIN никто не пришлёт, и `Read` будет висеть вечно.
Через 8 секунд полной тишины сокет считается мёртвым и закрывается: пинг-монитор
и так шлёт пробу каждые 2 секунды, так что тишина такой длины — это не задержка.

Дальше сессия **не заканчивается**, а замирает. Это возможно именно потому, что
протокол lockstep: ни одна сторона не может уйти дальше тика, на который у неё
есть команды всех игроков. Обе стороны останавливаются на одном и том же тике, и
единственное, чего не хватает, — нескольких команд, потерянных вместе с
соединением.

- Гость помнит последние 256 своих команд и при возврате повторяет их.
- Хост помнит свои и пересланные чужие, и повторяет их вернувшемуся.
- Приёмник игнорирует номера, которые уже видел, и выбрасывает те, что старше
  текущего тика. Поэтому повтор ничего не ломает и не требует подтверждений.

Состояние мира не передаётся ни в каком виде. Это не экономия, а причина, по
которой возврат вообще возможен: команда — это запись с номером, и обе стороны,
применив один и тот же набор, оказываются в одной и той же точке. Проверить это
можно только хешем: `NetReconnectTest` сверяет хеш применённых команд **потиково**,
а `tools/test-reconnect.ps1` рвёт реальное соединение через прокси и требует
совпадения хешей мира на 4000 тиках.

Три вещи при возврате **не** делаются, и каждая сломала бы сессию, а не просто
не сработала:

- **Слот не перевыдаётся.** Иначе вернувшийся получил бы чужие команды и чужой
  инвентарь, а стороны уже разошлись бы в том, кто такой игрок N.
- **Задержка ввода возвращается тем же числом.** Новый сокет на уже измеренном
  канале — не повод пересчитывать; подстройка (`DelayPolicy`) идёт своим чередом.
- **Мир не откатывается назад.** Догоняет всегда отстающая сторона, получая
  недостающие команды. Тот, кто ушёл вперёд, ничего не теряет.

Ожидание — 30 секунд. Если игрок так и не вернулся, сессия **не** завершается:
слот остаётся инертным, остальные играют (см. «Когда игрок уходит навсегда»).
Без токена (старый хост) или без адреса для повторного дозвона (хост) поведение
прежнее: обрыв завершает игру.

Relay работает так же: при потере гостя хост открывает новый канал у master,
хотя сессия формально заполнена, — иначе гость не смог бы вернуться через relay
вовсе.

## Когда игрок уходит навсегда

Раньше обрыв гостя, из которого он не вернулся, завершал сессию **для всех**.
Один плохой Wi-Fi закрывал игру остальным — это телефонный звонок, а не кооп.

Слот убрать нельзя: мир на трёх игроков и мир на двух — разные миры. От числа
слотов зависит, кто заспавнился, кого считает интермиссия и что делают монстры.
Мир при этом никак не передаётся, только команды, поэтому и «догнать» нового
состояния неоткуда.

Поэтому слот **остаётся, а игрок становится инертным**: хост присылает за него
пустые команды, то есть тело стоит там, где стояло. Все концы применяют одно и то
же, и никто не расходится. Сессия продолжается, остальные играют.

```
Net: lost 'guest' , holding the game for up to 30 s.
Net: 'guest' did not come back; player 2 is now inert and the session continues without them.
Net: player 2 left the game; the session continues without them.     <- на стороне гостя
```

Что важно в реализации и что уже один раз сломалось:

- **Пустые команды шлёт только хост.** Гость, который придумал бы их сам, выдумывал
  бы команды за чужой слот.
- **Только там, где у хоста нет настоящей команды.** Если команда игрока на этот тик
  успела прийти до обрыва, она уже есть у всех (ретрансляция идёт по TCP), и нулю
  поверх неё не место: где-то он был бы проигнорирован, а где-то применён — это и
  есть расхождение.
- **Генерация не под флагом «один раз за тик».** Флаг существует, чтобы бота не
  опрашивали дважды; пустые команды ни из чего не опрашиваются, и нужны именно на
  той попытке, которая завершает тик. За флагом сессия вставала намертво ровно на
  тике ухода — то есть ломалась в точности там, ради чего всё делалось.

**Гости должны знать, что игра стоит.** На их стороне всё в порядке: канал здоров,
и никакой команды, которую можно было бы запросить, не не хватает — тик просто
никогда не завершается. Без уведомления (`TypeHold`) это неотличимо от зависания:
на экране ничего, а `headless` считает это застоем и останавливает прогон. Это
была настоящая ошибка, и её нашёл живой прогон, а не юнит-тест.

**Срок ожидания проверялся только внутри `TryAdvance`** — а `Doom`, пока идёт
удержание, выходит из обработки **до** него. То есть «игрок не вернулся» не
наступало никогда: хост ждал вечно с надписью «WAITING FOR» на экране. Теперь
`PollReconnect` есть в интерфейсе драйвера и вызывается из той самой ветки.

**Вернуться после отказа нельзя.** Игра ушла вперёд, и вернувшаяся машина отстала
сильнее, чем окно повтора (несколько сотен команд — хватает на заминку, не хватает
на минуту игры). Догнать можно было бы только снимком мира, которого в lockstep
нет. Поэтому хост отвечает отказом с причиной:

```
Net: reconnect attempt failed (Host refused the connection: slot given up; new session).
```

Отказ — это **ответ, а не сбой**: `NetRefusalException` прекращает попытки сразу,
вместо пятнадцати секунд одинаковых строк в логе и «связь потеряна» в конце.
Заминка, сброс, таймаут — не ответ, их по-прежнему стоит повторять.

Обычное переподключение (в пределах срока) работает как раньше: хост держит игру,
никто не уходит вперёд, отстаёт только вернувшийся.

Проверка — `NetLeaveTest` (5, потиковые хеши выживших) и `tools/test-net-leave.ps1`
(три реальных процесса, третий убит без предупреждения, хеши на общем тике).

## Ограничения текущей версии

- Число игроков 2-4, только доверенная сеть: **без шифрования**. Пароль
  (`-password`) не пускает случайных людей, но сам идёт открытым текстом и ничего не
  скрывает. Relay снимает необходимость в пробросе порта, но не шифрует поток: master
  пересылает байты открытым текстом.
- Бан по адресу **не действует через relay**: хост видит адрес мастера, а не игрока.
  Остаются пароль и бан по нику. Это ограничение протокола, а не недоделка.
- Late join, dedicated server, сохранения в сети — нет. Ушедший игрок занимает
  слот до конца сессии: новый не может занять его место, потому что это был бы
  другой игрок в том же теле.
- Deathmatch-правила передаются, но режим не тестировался так же плотно, как coop.
- **4 игрока — жёсткий предел движка**, не настройка. Массивы игроков, формат
  демо и интермиссия рассчитаны на четыре слота. «До 1024» из задумок требует
  переписать их все и сломает совместимость демо — это отдельный проект, а не
  поднятие константы.
- Задержка ввода меняется на ходу, но только хостом и только по факту застоя: см.
  «Подстройка на ходу». Гость применяет решение, своё не принимает.
- Чат и консоль — не состояние игры: не входят ни в тик, ни в демо, ни в хеш.

## Проверка детерминизма

```powershell
# оба процесса считают одинаковый ввод для (тик, игрок)
dptdoom.exe -headless -iwad doom2.wad -net host -players 2 -port 5030 -tics 1500 -botinput
dptdoom.exe -headless -iwad doom2.wad -net join -address 127.0.0.1:5030 -tics 1500 -botinput
```

Оба печатают `State: mobj=... sector=...`. Совпадение хешей на одном и том же
тике означает, что симуляция на обеих сторонах идентична.

**Сравнивать надо на одном тике, а не по последней строке.** Стороны
останавливаются в разные моменты: хост досчитывает свои `-tics` и уходит, а гость
в этот момент ещё на пару тиков позже — он и получает «The other player left the
game». Чем глубже буфер ввода, тем шире этот зазор, поэтому сравнение финальных
`State:` ловит не расхождение мира, а разницу в моменте остановки. Для этого есть
`-stateat <n>`: он печатает `State@<n>:` ровно на достигнутом тике, и обе стороны
можно сравнить построчно. Все сетевые скрипты в `tools/` сравнивают именно так.

`-botinput` — только для тестов: это не бот-игрок, а детерминированная
последовательность команд, одинаковая на обеих машинах.

## Проверка скорости при задержке

```powershell
# 0, 50 и 100 мс в одну сторону (0, 100 и 200 мс пинга)
powershell -NoProfile -File tools\test-net-latency.ps1
```

Подделывает задержку через `tools/latency-proxy.ps1`, чтобы не искать напарника
на другом континенте. Падает, если скорость снова начнёт зависеть от round-trip.

Гоняет четыре канала: 0, 50 и 100 мс в одну сторону плюс отдельный случай
«50 мс ± 30 мс джиттера» — джиттер это другая задача для буфера, и без отдельного
случая он не проверялся бы вовсе.

Хосту даётся запас по тикам (`-HostLingerTics`). Без него хост добегает до своего
`-tics` первым и выходит, а гость остаётся с мёртвым портом: тратит весь срок
переподключения на неудачные дозвоны, и его измеренная скорость падает втрое на
сессии, которая на самом деле быстрая. Замер тогда меряет не задержку, а это.

Отдельно — замер **живого** игрового цикла, а не headless:

```powershell
powershell -NoProfile -File tools\measure-live-net.ps1 -DelayMs 50 -JitterMs 20
```

Headless симулирует так быстро, как позволяет сеть, и свободно догоняет, поэтому
показывает лучший возможный результат. Настоящая игра ограничена 35 тиками в
секунду и догонять без предела не может — рывок стоит реального времени. Разницу
видно только в живом цикле, поэтому это отдельный инструмент.

## Файлы

- `src/Net/NetProtocol.cs` — формат кадров.
- `src/Net/NetSession.cs` — TCP-транспорт, host/guest, ретрансляция тиков,
  измерение задержки.
- `src/Net/DelayPolicy.cs` — размер буфера ввода: начальная оценка и подстройка.
- `src/Net/ServerPassword.cs` — пароль сессии: сравнение по хешам без досрочного
  выхода и проверка при старте.
- `src/Net/BanList.cs` — правила бана: адрес, подсеть (IPv4 и IPv6), ник, маска,
  срок.
- `src/Net/ConnectionLog.cs` — журнал входов, выходов и отказов на диске хоста.
- `src/Net/NetDriver.cs` — lockstep-цикл, упреждение ввода и `INetDriver`.
- `src/Net/NetStartup.cs` — рукопожатие и ожидание игроков.
- `src/Net/WadChecksum.cs` — отпечаток набора WAD.
