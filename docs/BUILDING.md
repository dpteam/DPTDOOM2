# Сборка и запуск

## Требования

- Windows (основная и проверенная платформа).
- .NET SDK 9 или новее — **только чтобы собрать**. Сама игра собирается под
  .NET Framework 4.0 и работает без установленного .NET на Windows XP SP3+,
  Vista, 7, 8, 10, 11 (4.0 входит в Windows с Vista; на XP нужен .NET 4.0).
- Свой IWAD (`DOOM2.WAD`, `DOOM.WAD`, `FREEDOOM*.WAD`).

Пакет `Microsoft.NETFramework.ReferenceAssemblies` подтягивается NuGet-ом и нужен
только на этапе компиляции: это reference assemblies для net40, а не рантайм.

## Сборка

```powershell
dotnet build DPTDOOM.slnx -c Release
```

Результат:

```
DPTDOOM/bin/Release/net40/dptdoom.exe
DPTDOOM.Master/bin/Release/net40/dptdoom-master.exe
DPTDOOM.Launcher/bin/Release/net40/dptdoom-launcher.exe
```

Собрать один проект:

```powershell
dotnet build DPTDOOM\DPTDOOM.csproj -f net40 -c Release
```

## Запуск

```powershell
.\DPTDOOM\bin\Release\net40\dptdoom.exe -iwad refs\iwads\doom2.wad
```

Если IWAD лежит рядом с EXE, `-iwad` можно не указывать: игра ищет
`DOOM2.WAD`, `PLUTONIA.WAD`, `TNT.WAD`, `DOOM.WAD`, `DOOM1.WAD`,
`FREEDOOM2.WAD`, `FREEDOOM1.WAD`.

## Файлы пользователя

По умолчанию рядом с EXE: `dptdoom.cfg`, `doomsavN.dsg`.
Если рядом с EXE лежит `portable.txt`, всё уходит в `user/`.
`-userdir` перекрывает оба варианта — так лаунчер держит отдельные профили.

## Читы

Классические коды набираются в игре как обычно: `IDDQD`, `IDFA`, `IDKFA`,
`IDCLIP` (или `IDSPISPOPD`), `IDDT`, `IDMUSxx`, `IDBEHOLDx`.

`IDCLIP` проходит сквозь стены, вещи и монстров — это реализовано через
`CheckPosition`, который для ноуклип-игрока возвращается сразу, поэтому работает
и после смерти с респавном.

**Читы отключены в сетевой игре и при проигрывании демо.** Они меняют мир, а
вторая сторона об этом не узнает: lockstep разъедется, демо перестанет быть
демо. Это не ограничение реализации, а свойство читов — их нельзя передать по
сети так, чтобы это не сломало детерминизм.

## Тесты

```powershell
dotnet test DPTDOOMTest\DPTDOOMTest.csproj -c Release
```

- Тесты читают IWAD из каталога сборки тестов; `refs/iwads/*.wad` копируются
  туда автоматически при сборке.
- Без IWAD тесты совместимости помечаются пропущенными (`Inconclusive`), а не
  падают: репозиторий не содержит игровых данных.
- Геймплейные тесты сравнивают хеши состояния с эталонами Managed Doom.

Проверки вне MSTest:

Отдельно, это не тест: открыть порты в файрволе для хоста и master —

## Иконка

`resources/dptdoom.ico` содержит только классические DIB-кадры (16, 24, 32, 48,
64, 128). PNG внутри `.ico` Windows XP не понимает, поэтому исходный файл был
пересобран:

```powershell
powershell -NoProfile -File tools\fix-icon.ps1
```

Скрипт декодирует каждый кадр и пишет `BITMAPINFOHEADER` + BGRA-строки снизу
вверх + AND-маску, как ждёт XP. Прозрачность берётся из альфа-канала.

Окну иконка назначается дважды: в `WNDCLASSEX` (`hIcon`, `hIconSm`) и через
`WM_SETICON` после создания — часть оболочек берёт иконку задачи из окна, а не
из класса.

Упаковка для тестировщиков:

```powershell
powershell -NoProfile -File tools\package-build.ps1 -Version 0.1.0-local
# -> artifacts/dptdoom-windows-x64-0.1.0-local.zip
```

Всё это же выполняется в CI: [CI.md](CI.md).

## Скриншоты

```powershell
powershell -NoProfile -File tools\capture-game.ps1     # кадры движка
powershell -NoProfile -File tools\capture-showcase.ps1 # лаунчер, обе темы
```

## Проверка звука

Звук нельзя оценить по скриншоту, поэтому микшер можно отрендерить в файл:

```powershell
dptdoom.exe -headless -iwad doom2.wad -soundtest sfx.wav
```

Пишет два файла:

- `sfx.wav` — эффекты по очереди;
- `sfx-mixed.wav` — все одновременно (худший случай по перегрузу).

Рендер идёт через тот же `SoundMixer`, что и игра, поэтому слышно ровно то, что
услышит игрок. Конкретные звуки: `-sfx PISTOL,SHOTGN,CLAW`.

Отдельно проверяются юнит-тестами: `SoundMixerTest` (перегруз, ресемплинг,
громкость, детерминизм) и `SoundPanTest` (сторона источника, constant-power
панорама, затухание по расстоянию).

## Проверка плавности

Подёргивание картинки нельзя оценить на глаз, поэтому есть лог тайминга:

```powershell
dptdoom.exe -iwad doom2.wad -fpslog fps.tsv
```

Одна строка на кадр:

```
frame  nominal_ms  interval_ms  render_ms  present_ms  wait_ms  tics  frac
```

- `interval_ms` — реальный интервал между кадрами; при 70 fps цель 14.286 мс.
- `render_ms` — софтверный рендер.
- `present_ms` — вывод кадра в окно через GDI.
- `wait_ms` — сколько цикл простоял, ожидая следующий кадр.
- `tics` — сколько тиков симуляции прошло на этом кадре (обычно 0 или 1).
- `frac` — доля интерполяции, должна расти внутри тика.

Здоровый прогон: `interval` около цели, `frac` монотонно растёт и сбрасывается
только на кадре с `tics>0`. Если `present_ms` большой — узкое место в выводе, а не
в движке.

## Экран настроек и консоль

### Экран настроек

Меню «Опции → Настройки» (и `-showsettings`). Отдельный экран, потому что классические
меню Doom собраны из патчей, которые нарисовал id Software в 1994 году: патча для
прицела или обзора мышью не существует, а рисовать свои меню-картинки — значит
тащить графику, которой у проекта нет.

Всё, что появилось после 1994 года, живёт здесь, на одном экране: прицел, обзор
мышью, сообщения, размер вида, гамма, громкости, чувствительность, «всегда бежать»,
профиль кадра. Экран нарисован **шрифтом самой игры**, поэтому работает с любым
IWAD — включая тот, где все меню-графики заменены.

Вёрстка — сетка из четырёх чисел (ширина панели, высота строки, отступ сверху,
отступ снизу), и каждая координата выводится из них. Это и есть причина, по которой
экран не выходит кривым: ничего не позиционируется прибавлением подобранного на глаз
смещения к предыдущему элементу. Первая версия была именно такой и в результате
рисовала подсказку прямо поверх последней строки — два числа, посчитанные в разных
местах, разошлись на три пикселя.

Панель центрируется по **виду**, а не по окну: иначе она наезжает на статус-бар и
закрывает здоровье игрока ровно в тот момент, когда он меняет громкость.

### Консоль

Клавиша `~` открывает консоль (в игре и в демо; на титульном экране она не нужна и
перекрыла бы заставку). `Esc` или `~` закрывают, `Enter` выполняет и оставляет
консоль открытой — иначе она была бы одноразовой строкой ввода. `Tab` дополняет по
общему префиксу, `↑`/`↓` листают историю, `PgUp`/`PgDn` — прокрутку.

Команды:

| Команда | Что делает |
|---|---|
| `help [name]` | список команд или справка по одной |
| `clear` | очистить прокрутку |
| `echo <текст>` | напечатать обратно |
| `version` | версия сборки |
| `god`, `noclip` | переключатели (как `iddqd`, `IDCLIP`) |
| `give <all\|weapons\|ammo\|keys\|saw>` | выдать оружие, патроны, ключи |
| `powerup <v\|s\|i\|r\|a\|l>` | один артефакт (как `IDBEHOLDx`) |
| `killem` | убить всех монстров |
| `revealmap` | полный automap |
| `cheats` | можно ли сейчас читерить и почему нет |
| `crosshair <0..3\|off\|cross\|dot\|both>` | прицел |
| `freelook <on\|off>` | обзор мышью |
| `sensitivity <1..9>` | скорость мыши |
| `volume <sfx\|music> [0..max]` | громкость |
| `gamma <0..max>` | яркость |
| `screensize <0..max>` | размер вида |
| `alwaysrun`, `messages`, `profile <on\|off>` | переключатели |
| `map <MAP32\|E1M1\|1..32>` | начать уровень (только одиночная игра) |
| `players` | кто в сессии |
| `quit` | выйти |

Что важно:

- **Консоль забирает все клавиши.** `Handle` возвращает true на любое событие, а не
  только на те, что обрабатывает: иначе набранный `iddqd` сработал бы читом, а цифра
  переключила размер вида. То же самое с подавлением движения — пока консоль открыта,
  `userInput.Suppressed` включён, иначе `wasd` в команде уводил бы игрока.
- **Команд, меняющих симуляцию, нет** — кроме читов, и они подчиняются тому же
  правилу, что и набранные коды: в сети и в демо **отказываются**. Чит меняет мир,
  вторая сторона об этом не узнает, и lockstep расходится; отправить чит по сети не
  спасает — это отладочный инструмент, а не игровая возможность. `cheats` говорит,
  можно ли сейчас, и почему нет.
- **`give` — не одно и то же, что `idkfa`.** `give weapons` даёт арсенал без ключей:
  игрок, просящий оружие, не просит открыть все двери. `give all` — это `idkfa`,
  потому что «всё» значит всё. `give keys` даёт только ключи, без арсенала.
- **Коды и команды идут через один диспетчер** (`Cheat.Execute`, `CheatAction`).
  Две реализации «что делает god mode» разошлись бы, и разошлась бы та, которую
  никто не тестирует.
- **Консоль — оверлей, а не экран.** Она занимает верх, а низ вида остаётся виден:
  ради этого её и открывают. Панель не заливка, а затемнение через `COLORMAP` —
  комнату видно сквозь неё, как через стекло, а не через сетку пропущенных пикселей.
- Цвета берутся из `PLAYPAL` через `PaletteLookup.Tint`: шрифт Doom затенён, и
  заливка одним цветом превратила бы буквы в силуэт. Таблица переводит каждый индекс
  в ближайший к «целевой цвет × его яркость», поэтому буква сохраняет объём.

Проверки: `GameConsoleTest` (21 тест: ввод, история, дополнение, прокрутка,
исполнение, отказ, перехват), `CheatActionTest` (9: диспетчер, переключатели,
разница между `give weapons` и `give all`, отказ). Скрипты: `tools/test-console.ps1`
и `tools/test-cheats.ps1` — экраны рисуются и не задевают статус-бар; каждая
команда меняет мир по-своему; чит в сети отказывается и мир не расходится.

## Прицел и обзор мышью

**Прицел.** Четыре состояния, переключаются пунктом меню «Вид → Прицел» или флагом
`-crosshair`:

| Значение | Что рисуется |
|---|---|
| 0 | ничего |
| 1 | крест (по умолчанию) |
| 2 | точка |
| 3 | крест с точкой в центре |

Крест оставляет центр пустым намеренно: точка поверх цели закрывает то, во что
целятся, а перекрестие с разрывом — нет. Рисуется двумя проходами, тёмным на пиксель
шире и светлым поверх: белый крест исчезает на светлой стене, чёрный — в тёмном
коридоре. Индексы палитры для обоих находятся поиском ближайшего цвета в `PLAYPAL`,
а не зашиты числом: в Freedoom индекс 4 — не тот же цвет, что в Doom II, и прицел
фиксированного цвета там просто не видно.

**Обзор мышью** (как в Duke Nukem 3D). Включается пунктом «Вид → Обзор мышью» или
`-freelook`. Вертикальная ось мыши начинает наклонять вид вместо того, чтобы вести
игрока вперёд-назад; `PageUp`/`PageDown` наклоняют с клавиатуры, `End` возвращает
взгляд в горизонт. Наклон ограничен ±70 виртуальных пикселей (треть экрана): дальше
скос начинает читаться как растянутые плоскости у края, а не как «смотрю вверх».

Что важно понимать:

- **Это обзор, а не прицеливание.** Стрельба по-прежнему идёт через ванильный
  2D-автоприцел Doom: наклон меняет то, что видно, но не то, во что попадает пуля.
  Так сделано не из лени — вертикальное прицеливание требует переписать
  `AimLineAttack` и весь обсчёт попаданий, а это меняет симуляцию и, значит,
  совместимость демо. Поэтому в меню написано «обзор», а не «прицеливание».
- **Наклон не входит в состояние игры.** Он не попадает ни в `TicCmd`, ни в демо, ни
  в сохранение, ни в хеш мира: два игрока в одной сессии могут смотреть в разные
  стороны по вертикали, и симуляция этого не заметит. Проверка —
  `ViewPitchTest.PitchIsNotPartOfTheWorld`.
- **Оружие не следует за наклоном.** Оно в руках игрока, и ствол, уезжающий вверх
  вместе с горизонтом, читается как пла whatever. Спрайт оружия позиционируется от
  несмещённого центра, и на время его отрисовки `centerY` тоже возвращается к
  базовому — иначе спрайт остаётся на месте, но показывает не ту часть своей
  текстуры.
- **Горизонт двигается скосом проекции**, а не поворотом камеры: `centerY` и
  `centerYFrac` смещаются вместе, и стены, плоскости и спрайты уезжают вместе с ними.
  Сдвинуть только одно из двух — значит сдвинуть геометрию относительно её текстур.

Проверки: `ViewPitchTest` (5 тестов) и `tools/test-view.ps1` (четыре стиля прицела,
наклон, зажим, отрицательный `-pitch`).

## Профиль кадра по секциям

`render_ms` говорит, сколько занял кадр, но не говорит, **на что**. Второй лог —
профиль по секциям:

```powershell
dptdoom.exe -iwad doom2.wad -profile
```

Отчёт печатается при выходе, а в окне при включённом профиле идёт компактная
строка `prof bsp ... spr ... hud ... conv ...`.

```
Render profile over 199 frames (1.82 ms per frame, worst 3.04 ms):
  setup      0.00 ms   worst 0.00
  bsp        1.15 ms   worst 1.25
    walls      0.29 ms   worst 0.35
    flats      0.57 ms   worst 0.64
  sprites    0.01 ms   worst 0.02
  masked     0.00 ms   worst 0.02
  player     0.01 ms   worst 0.02
  sky        0.00 ms   worst 0.00
  convert    0.47 ms   worst 0.53
  hud        0.17 ms   worst 0.22
  per frame: segs 44.0 wall columns 1629.0 flat columns 4374.0 sprites 8.0 masked 0.0
```

Числа выше — MAP01, стартовая комната, 640×400, net40. Они зависят от машины и
карты, поэтому важны не абсолютные значения, а соотношения: на этой сцене
плоскости дороже стен в два раза, а конвертация палитры в 32-битный кадр стоит
столько же, сколько все стены вместе.

Что и зачем:

- **Секции верхнего уровня складываются в кадр.** `test-profile.ps1` это
  проверяет: сумма обязана попасть в 80–115 % от `per frame`. Секция, выпавшая из
  суммы, — это время, которое никто не сможет оптимизировать, потому что его не
  видно.
- **`walls` и `flats` вложены в `bsp`** — они рисуются внутри обхода BSP. Отсюда
  отступ в отчёте: `bsp` минус `walls` минус `flats` — это собственно обход.
  Складывать все четыре нельзя, поэтому и проверка на двойной счёт отдельная.
- **Счётчики рядом с таймингами** — потому что «плоскости 4 мс» значит разное на
  640×400 и на 1600×1200, и привести к общему знаменателю можно только зная,
  сколько колонок нарисовано.
- **`convert`** — запись кадра в 32-битный буфер для GDI. Она не в движке, но
  занимает четверть кадра, и без неё профиль бы врал о том, куда уходит время.

Профилировка **не меняет ни кадр, ни симуляцию**, и это проверяется, а не
предполагается: рендерер помечает линии как увиденные для automap и берёт
`validCount` из мира, то есть рисовать каждый тик вместо ни одного — ровно тот
приём, который способен сдвинуть хеш. `tools/test-profile.ps1` сравнивает BMP
байт-в-байт и хеш мира с прогоном без `-profile`.

Стоимость самой профилировки: пара чтений счётчика на колонку. На этой сцене это
проценты, не больше, но числа профиля — верхняя оценка, а не точное время
«честного» кадра.

### Симуляция идёт по часам, а не по кадрам

Это важно при разборе «кажется, будто FPS ниже, чем показывает счётчик».

35 тиков в секунду должны происходить в каждой реальной секунде, даже если
нарисовалось только 40 кадров. Раньше мир обновлялся на кадре с
`frame % fpsScale == 0`, то есть частота тиков была привязана к числу
нарисованных кадров. На большом окне кадры не успевали — и игра замедлялась
вместе с ними: пистолет стрелял реже, хотя счётчик кадров показывал норму,
потому что счётчик считает кадры, а оружие — тики.

Замер на этом же билде: окно 2400×1400, цель 140 fps, машина выдаёт 115 fps.
Тиков всё равно 34.7 в секунду. Со старой схемой было бы 115 / 4 ≈ 29 в секунду,
то есть на 17% медленнее.

Сводка в конце прогона печатает тики отдельно от кадров:

```
Frames: 856
Target: 140.0 fps (7.14 ms)
Average interval: 8.64 ms (115.7 fps)
Tics: 257 (34.7 per second, should be 35)
Late frames: 0, worst 0.00 ms
```

Догоняние ограничено: не больше 4 тиков на кадр и не больше 0.25 с отставания за
один провал. Иначе одно зависание (перетаскивание окна, диск) накопило бы очередь
тиков, следующий кадр стал бы ещё медленнее, и цикл не восстановился бы. Лучше
на мгновение замедлиться, чем замерзнуть.

## Меню окна и трей

В оконном режиме есть обычное меню Win32 — как у программ той эпохи, под
которую сделан порт. Оно нужно потому, что не всё выражается клавишами:
громкость, размер окна, гамма и отладочные инструменты должны быть
обнаружимы, а не спрятаны в биндах.

```
Игра     Новая игра, Следующая карта, Сохранить (F2), Загрузить (F3),
         Пауза, Выход (F10)
Вид      Полный экран, Размер окна (320/640/960/1280), Гамма ярче/темнее,
         Сообщения (F8), Счётчик кадров
Звук     Эффекты/музыка громче-тише, Без эффектов, Без музыки
Отладка  Лог кадров в файл, Сохранить кадр в BMP, Сбросить состояние мира,
         Отрендерить звуки в WAV, Бог, Сквозь стены, Всё оружие и патроны
Справка  Управление (F1), О программе
```

Пункты с галочками отражают реальное состояние: полный экран, сообщения,
счётчик, лог, читаемость чит-флагов, выключенный звук.

**Трей.** Пункт «Свернуть в трей» прячет окно и оставляет иконку в области
уведомлений: двойной клик возвращает окно, правый клик открывает меню (показать,
свернуть, счётчик кадров, лог, кадр, выход). Это поведение фоновых программ
Windows 3.x, и оно удобно, когда игра ждёт напарника.

**Счётчик кадров.** Рисуется поверх кадра средствами GDI, а не в кадровом
буфере: отладочная информация не должна попадать в сохранённые кадры и в
сравнения хешей.

**Отладочные файлы** пишутся в `debug/` и `screenshots/` внутри каталога данных
(`user/` в portable-режиме), чтобы не смешиваться с бинарниками.

Меню и трей проверяются `tools/test-menu.ps1`: он шлёт те же `WM_COMMAND`, что
и клик, и проверяет, что состояние действительно изменилось (размер окна,
полный экран, скрытие в трей), а не только что пункт существует.

## Упаковка

Каждый крупный апдейт пакуется в готовый ZIP:

```powershell
powershell -NoProfile -File tools\package-build.ps1 -Version 0.2.0
# -> artifacts/dptdoom-windows-x64-0.2.0.zip
```

Внутри: `dptdoom.exe`, `dptdoom-master.exe`, `dptdoom-launcher.exe`,
`DPTDOOM.Shared.dll`, лицензия, `READ-ME-FIRST.txt` и `source.zip` — исходники
того же коммита (GPL). IWAD, конфиги, сохранения и логи в пакет не попадают;
упаковщик явно отказывается их класть.

CI собирает такой же архив в артефактах на каждый пуш
(`dptdoom-windows-<commit>`).

## Ограничения

- Проверено на Windows 10/11 с .NET Framework 4.8 и на .NET 9 SDK.
  Реальный запуск на Windows XP **ещё не проверялся** — код и API подобраны под
  XP (user32/gdi32/winmm, без LINQ-новинок, без `MathF`, без `Span`), но это
  требует отдельной машины или виртуальной среды.
- Linux/macOS сборка сейчас не поддерживается: Win32-бэкенд основной.
  Переносимые точки — `IVideo`, `ISound`, `IMusic`, `IUserInput`; headless уже
  платформенно-нейтрален.
- Звук проверен на реальном железе через `waveOut`; MIDI зависит от системного
  синтезатора (на XP это Microsoft GS Wavetable SW Synth).
