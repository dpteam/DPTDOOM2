## 4. Сеть

- [x] Lockstep TCP host/join на 2–4 игроков.
- [x] Сверка digest WAD перед стартом.
- [x] Статус подключения шрифтом Doom.
- [x] Проверено: 1500 тиков, хеши мира у хоста и гостя совпадают.
- [x] Упреждение ввода: при 100 мс пинга 57 тиков/с вместо 17.5.
- [x] **Reconnect после обрыва.** Обе стороны замирают на одном и том же тике:
  lockstep не даёт уйти дальше, чем есть команды. Поэтому состояние мира
  передавать не нужно — достаточно дослать команды, потерянные вместе с
  соединением. Гость хранит последние 256 своих команд и повторяет их при
  возврате; хост повторяет свои и пересланные чужие. Слот не перевыдаётся:
  иначе вернувшийся получил бы чужие команды. Задержка ввода при возврате
  возвращается тем же числом, каким была. Ожидание 30 с; если игрок так и не
  вернулся, сессия **не** завершается — слот остаётся инертным и остальные играют
  (см. раздел 12, «Ушедший игрок не завершает сессию»).
  Проверки: `NetReconnectTest` (4 теста, хеш применённых команд обеих сторон
  сверяется потиково), `tools/test-reconnect.ps1` — реальный разрыв через
  прокси, хеши мира совпали на 4000 тиках; `NetLeaveTest` и
  `tools/test-net-leave.ps1` — уход без возврата.
- [ ] **Late join** - подключение к идущей игре.
- [ ] Dedicated server.
- [x] Relay через master: TCP-прокси, хост без проброса порта, NAT hairpin.
- [x] Чат в игре: `T` открывает строку, `Enter`/`Esc`, хост пересылает гостям.
- [ ] Голосовой чат.
- [x] `dmflags`: `-noblock` (игроки сквозь друг друга), дубли DM-оружия, общие ключи.
- [ ] Сессия с настраиваемым max игроков: 2–4 сейчас, предел движка. До 1024 —
      отдельный проект (массивы игроков, формат демо, интермиссия).

- [x] Бот не замирает: triedSector сбрасывается при входе в новый сектор.
- [x] Маршрут к выходу ищется до любой точки сектора (FindPathToSector).
- [x] MAP01 проходят все 4 стиля (0:32-0:59); время печатает headless при смене карты.
- [x] Боты в сетевой игре: водит хост, команды идут по сети; тест `tools/test-net-bots.ps1`.
- [x] Диагностика: `BotReachabilityTest` печатает special, перепад, просвет и высоты пола/потолка.
- [x] Отступление при низком здоровье — у всех стилей, не только Cautious (Hunter проходит UV).
- [x] Тест выживания: на skill 3 смерти запрещены (`BotSurvivalTest`), skill 4 печатается.
- [ ] Бой на Ultra-Violence: Rush гибнет 10 раз, Cautious 9, Sweeper 4. Нужна не
      связность, а выживание — расширение маршрутов только добавляет способов умереть.
      Опровергнуто замером: «лечись при низком HP» (смерти падают, но бот теряет
      маршрут к выходу и не доходит) и «выбирай оружие по дистанции» (числа не
      изменились: на MAP01 дробовик годен на всех встречающихся дистанциях).
      Следующий шаг — возврат к маршруту после крюка за здоровьем, либо тактика
      против hitscan. Подробности — docs/BOTS.md.
- [ ] Оценка обстановки: «могу ли я пройти мимо» вместо «вижу — стреляю».
- [x] Сетевые боты: хост отправляет `TicCmd` бота по сети (см. выше,
      `tools/test-net-bots.ps1`).
- [x] **Боты: спам дверей.** Причина найдена в движке: `UseSpecialLine` на «открывающей»
      двери при живом thinker'е переворачивает направление `+1` → `-1`, то есть
      нажатие на движущуюся дверь её **закрывает**. Бот жал `Use` каждый четвёртый тик,
      пока стоял на дверной ноге, и открывал-захлопывал её. Теперь есть
      `IsDoorPressable`: жать только там, где это двигает дело (нет thinker'а и низкий
      потолок). Проверка — `BotDoorTest` (2) и счётчик нажатий **на дверных ногах** в
      `tools/test-bots.ps1`: 6 нажатий на прогон через два десятка дверей.

      Отвергнуто и записано, чтобы не предлагали снова: реже жать (раз в секунду, раз
      в восемь тиков) — ломает прохождение MAP01, редкий импульс промахивается мимо
      окна; жать и на закрывающейся двери — бот жмёт каждые четыре тика и дверь не
      завершает цикл никогда (четыре бот-теста перестали проходить MAP01).

- [x] **Боты: долбёжка в стену и орбита вокруг недостижимой точки.** Две отдельные
      причины, обе видны в трассе:

      1. обработчик «застрял» штрафовал саму точку, а если она и есть цель маршрута,
         штраф ничего не решает — поиск обязан до неё дойти. Теперь цель помечается
         `triedSector`, а флаг очищается при входе в новый сектор;
      2. в графе есть **односторонние карманы** — это осознанное свойство (с уступа
         можно спрыгнуть и нельзя влезть). Из района сектора 43 на MAP01 достижимы
         6 секторов из 59, выхода среди них нет. Добавлены `CanStillLeave` (обход не
         выбирается, если из его конца выход недостижим) и `retreat` назад к последней
         точке, откуда выход был достижим. Проверка — `BotPocketTest`.

- [x] **Боты: обучение и честность теста.** `bots/*.brain` — настоящее состояние между
      прогонами, и тест, читающий каталог рядом с exe, измерял накопленный файл:
      «зелёно» скрывало, что Sweeper с чистым мозгом не проходит MAP01. Добавлены
      `-nobotbrain` и `-botbraindir <каталог>`; `tools/test-bots.ps1` работает во
      временном каталоге, делает прогревочный прогон и измеряет второй. Замер после
      правок: Rush 1933, Sweeper 1461, Hunter 1337, Cautious 2045.

      **Найдено позже и исправлено:** проверка «можно ли выйти» смотрела только на
      цель маршрута, а граф направленный — маршрут к безопасной цели проходил **сквозь**
      односторонний спуск, и бот запирался на дальнем конце (Sweeper: 3219 тиков «нет
      маршрута» из 3999). Теперь проверяется каждый сектор маршрута
      (`RouteStaysEscapable`, кэш по сектору), а «я в ловушке» считается по сектору
      бота, а не по ближайшему узлу — тот мог принадлежать комнате, из которой бот
      только что выпал. Подробности — `docs/BOTS.md`.

## 9. Совместимость и контент

- [x] DeHackEd (подмножество).
- [x] **PK3/ZIP как контейнер**: свой читатель ZIP (`ZipArchiveReader`) на
      `DeflateStream`, потому что `ZipArchive` появился только в .NET 4.5, а
      целевая платформа — 4.0 для XP. Внутри PK3 грузятся WAD (рекурсивно) и
      отдельные люмпы. Режим игры определяется по картам (`MAP01` / `E1M1`), а не
      по имени файла, иначе контейнер с произвольным именем не опознавался.
- [x] **PNG-графика из PK3**: свой декодер PNG (`PngImage`) — тоже без сторонних
      библиотек. Плоскости из `flats/*.png` декодируются, масштабируются в 64×64
      и переводятся в индексы PLAYPAL; плоская текстура из PK3 переопределяет
      одноимённую из IWAD.
- [x] **Текстуры стен и спрайты из PK3**: PNG переводится в формат патча Doom
      (`Pk3Graphics.ToPatch`) — колонки с «постами», прозрачность как отсутствие
      пикселя. `textures/NAME.png` заменяет одноимённую стену, `sprites/POSSA1.png`
      (или `POSS A1.png`) — спрайт, с якорем по центру нижней кромки.
- [ ] ZDoom `TEXTURES` — язык описания составных текстур. Сейчас поддерживается
      только простая форма «один PNG на текстуру».
- [ ] Interlaced PNG (Adam7): сейчас отвергается с внятной ошибкой.
- [~] **DECORATE — через конвертацию в SharpScript.** Готова первая половина: блоки
      акторов читаются, числа и флаги применяются, остальное честно сообщается.
      Описано в `docs/DECORATE.md`. Проверка: `DecorateConverterTest` (15, включая
      применение сгенерированного текста к настоящей таблице акторов) и
      `tools/test-decorate.ps1` (живой прогон: хеш мира меняется от чисел в `.dec`;
      лампа `DECORATE` в PWAD находится без ключа и даёт тот же мир, что путь к файлу).

      Что сделано и почему именно так:

      - **конвертация, а не второй путь применения.** У SharpScript уже есть разбор,
        песочница и один проход применения, проверенные против таблицы акторов. Второй
        путь потребовал бы своей копии всех трёх, и копии разошлись бы — а расхождение
        здесь значит, что один актор меняется по-разному в зависимости от языка описания;
      - **номера и флаги переносятся, `States` — нет.** Кадру нужна запись в таблице
        состояний и имя спрайта, а патч актора не может ни того, ни другого. Соврать здесь
        значит получить актора, который выглядит сконвертированным, а ведёт себя как
        оригинал;
      - **имена акторов — только монстры.** Неверный номер не падает, а тихо правит
        другого актора: таблица, вспомненная по памяти, хуже её отсутствия. Остальное —
        строка отчёта, и моддеру это стоит одной строки правки;
      - **`MONSTER` и `PROJECTILE` расширяются по ванильному Doom**, а не по догадке:
        ракета — это `MF_NOBLOCKMAP|MF_MISSILE|MF_DROPOFF|MF_NOGRAVITY`;
      - **пустой патч не пишется**: `fn Thing_...()` без содержимого выглядел бы в отчёте
        как сделанная работа;
      - **`scripts: OK` при непреобразованных состояниях — намеренно.** Скрипт, который не
        разобрался, — провал; состояния, которые движок не принимает, — нет: числа
        сработали. Называть это «Failed» каждый раз, когда мод содержит `States` (то есть
        всегда), значит научить игрока не читать слово.

      Что осталось: `States` теперь переносится (см. `docs/DECORATE.md`), поэтому остались
      реакция на события (урон, попадание), замена звуков по имени люмпа — сейчас
      `SeeSound "imp/sight"` честно попадает в отчёт как неперенесённое — и параметры
      действий вида `A_LookEx(...)`, которых у действий этого движка нет.

      **Как сделаны состояния** (чтобы не искать заново). `Mobj.State` держит
      `MobjStateDef`, но продвижение идёт через перечисление: `Mobj.SetState(MobjState)`
      делает `DoomInfo.States[(int)state]`. Значит произвольный объект состояния в игру не
      поставить, и понадобился хвост:

      1. ванильный литерал таблицы переименован в `VanillaStates` (приватный), а
         `DoomInfo.States` стал свойством: копия ванильных записей плюс резерв.
         **В хвост, не в середину** — номера состояний входят в формат сохранений и в хеши
         мира;
      2. `CustomStateReserve = 1024` слота, заполненных `Null`-подобным состоянием: не
         зарегистрированный кадр убирает моба, а не роняет игру;
      3. `Number` обязан совпадать с индексом — это читает `SaveAndLoad`
         (`DoomInfo.States[BitConverter.ToInt32(...)]`);
      4. имена действий строятся **рефлексией** по `MobjActions` (та же partial-часть,
         поэтому приватный `ma` виден): каждое действие — метод ровно с подписью
         `(World, Mobj)`, и имя `A_<Метод>`. Пятьдесят две записи руками — пятьдесят две
         возможности опечататься и разойтись с кодом;
      5. спрайты ищутся по `DoomInfo.SpriteNames` (индекс = `(int)Sprite`), а не по имени
         перечисления: у дробовичника спрайт `POSS` в WAD и `SHTG` в перечислении.

      Коллизий имён нет: последовательность `See:` **заменяет** `SeeState` актора головой
      новой цепочки, а `Goto See` внутри секции разрешается в голову своей цепочки, если
      она определена, и в ванильное `SeeState`, если нет.

      Ловушка, на которой это ловится: **порядок статических инициализаторов между
      partial-файлами не определён**. Первая версия читала `VanillaStates.Length` в
      поле-инициализаторе и получала `NullReferenceException`, потому что соседний файл
      ещё не выполнился. Поэтому `CustomStateFirst` — свойство.

## 12. План развития: идеи и приоритеты

Записано, чтобы идти постепенно и не терять замыслы. Порядок — по стоимости и по
тому, насколько пункт разблокирует остальные. **Мультиплеер и DECORATE идут раньше
всего остального в этом списке** — это то, что нужно в первую очередь.

Мультиплеер здесь — не только «догнать по функциям». Чтобы хостить для друзей,
нужны пароль, банлист и снятие квот для своих; без них «полный функционал» упирается
не в код, а в доверие. Поэтому четыре пункта про сервер идут сразу за ним.

После DECORATE — SharpScript: тот же замысел, но на C#, потому что грамматику
DECORATE приходится угадывать по чужим реализациям, а C# уже описан.

### Ближайшие

- [ ] **Мультиплеер: полный функционал и оптимизация.** Тестируется с друзьями, в том
      числе в одиночке, поэтому это первое. Что осталось: late join, dedicated server
      (headless уже есть, но это не он).
- [x] **Пароль на сервер.** Чтобы хостить для друзей, не пуская случайных людей.
      Ложится в необязательный хвост `HELLO` (бит в флаговом байте, блок после
      токена возврата) и сверяется хостом **до** `WELCOME`; неверный — отказ с
      причиной, и `NetRefusalException` не даёт переподключению молотить впустую.
      Проверка: `ServerPasswordTest` (15), включая живую сессию с паролем и
      отсутствие пароля в `SessionSettings` и в отчёте.

      Сравнение — по хешам фиксированной длины без досрочного выхода: побайтовое с
      выходом на первом различии даёт подбор посимвольно по времени ответа. Пароля
      нет ни в `SessionSettings` (они едут в приветствии и публикуются мастеру), ни в
      логе, ни на экране — там `PASSWORD ON`. Возврат по токену пароль не спрашивает:
      иначе смена пароля выкидывала бы из игры тех, кто уже в ней. И честно в UI и
      документации: это **не** шифрование, пароль идёт открытым текстом.

      Две ловушки: `-password -secret` читается как «пароля нет» (значение с ведущим
      дефисом похоже на следующую опцию) — теперь это ошибка, а не тихо открытая
      сессия; и поле в лаунчере сначала ничего не делало, потому что его не подключили
      к обработчику перерисовки.
- [x] **Банлист и логирование на хосте.** Часть уже была **на мастере** (CIDR +
      срок, отказ до всякой игры, запись в лог), но ников и «кто вышел» мастер не
      видит и увидеть не может: он видит открытие и закрытие туннеля, не содержимое.
      Поэтому появился свой слой на хосте: `BanList` (адрес, подсеть IPv4/IPv6, ник,
      маска `*`, срок `until`) и `ConnectionLog` (join / resume / leave с причиной /
      refuse с причиной и правилом). Формат правил — надмножество мастерского, чтобы
      один файл годился обоим.
      Проверка: `BanListTest` (23), `HostBansTest` (8), `tools/test-host-bans.ps1`.

      Четыре решения, каждое из которых легко было принять неправильно:
      - **проверка после `HELLO`, а не сразу после `accept`.** Закрыть сокет с
        непрочитанным кадром в буфере — значит отправить сброс, и гость увидит
        «connection reset by peer» вместо «banned». Сказать, что забанен, — весь смысл;
      - **бан проверяется до ветви возврата по токену**, иначе забаненный, который уже
        в игре, спокойно переподключится;
      - **в relay адрес неизвестен** (`address=-`): хост видит мастера, а не игрока.
        Бан по адресу там неприменим, и это записано, а не замаскировано;
      - **причина в строке ухода обязательна.** `leave` без неё не отличает «вышел
        сам» от «умер роутер» от «махнули рукой» — три разные вещи для разбора.

      Побочно нашлась настоящая гонка: `Dispose` и `Finish` перебирали список пиров,
      пока их циклы чтения удаляли оттуда пиры. Исключение «collection was modified»
      прилетало в `Dispose` — худшее место для него. Теперь список копируется под
      замком, и то же сделано для пересылки тиков и чата.
- [x] **Allowlist на мастере: снять квоты для своих.** `AllowListOnly` у мастера уже
      закрывает доступ списком, но **квоты не снимал**: relay держал
      `RelayGuestsPerSession` (3) и `RelaySessionsPerSource` (2) для всех одинаково.
      Теперь правило allow-списка может нести подъём: `sessions-per-source N`,
      `guests-per-session N`, `links-per-source N`, `sessions-total N` — имена как
      в конфиге, чтобы не держать в голове второй словарь.
      Проверка: `tools/test-master-allow.ps1` (два мастера с одинаковыми малыми
      квотами: без правила останавливается на них, с правилом идёт дальше).

      Три ограничения, каждое из которых иначе было бы ловушкой:
      - **подъём только повышает.** Меньшее число, чем в конфиге, ничего не
        ужесточает: allow-список — список разрешений, а ужесточать надо в конфиге,
        где это видно всем. Проверено отдельным случаем в скрипте;
      - **`sessions-total` не расширяет общий потолок для чужих** — он даёт адресу
        собственный потолок **вместо** общего, поэтому дав одному месту, нельзя
        впустить в него остальных;
      - **гостевую квоту поднимает правило хоста, а не гостя.** Размер группы
        выбирает хозяин; иначе любой приводил бы толпу в чужую игру.

      При пересечении правил действует **наибольшее** число, а не первое совпавшее:
      `/8` для семьи и `/32` для одной машины — нормальный файл, и ответ не должен

      интерпретатор, песочница и API свойств актёра. Описано в `docs/SCRIPTS.md`.
      Проверка: `ScriptLanguageTest` (44), `ScriptActorTest` (17),
      `tools/test-scripts.ps1` (живой мир: скрипт меняет хеш мира, битый скрипт не
      рушит игру, отсутствующий файл не останавливает загрузку).

      Что сделано и почему именно так:

      - **свой язык, а не встроенный C#.** Любой встраиваемый C# требует рантайма, а
        рантайм — это ровно то, чего не должно быть у скачанного PWAD; Roslyn —
        сторонняя DLL, `CodeDom` на XP нет. Свой интерпретатор подмножества даёт XP и
        кроссплатформенность бесплатно;
      - **песочница — свойство грамматики.** Точки в языке нет вообще, поэтому
        `File.Read(...)` — синтаксическая ошибка, а не «заблокированный член». Список
        запрещённых вызовов не нужно держать в согласии с BCL, потому что пути к BCL
        нет;
      - **fixed-литералы разбираются из цифр целочисленной арифметикой.** `0.1` — это
        6554/65536, значение движка; через `double` получается 6553 или 6555 в
        зависимости от платформы, и это расхождение моддер нашёл бы там, где не ждал;
      - **бюджет 100000 шагов и глубина 32.** В языке есть `while`, а цикл внутри
        игрового цикла — зависание с нарисованным окном;
      - **повторное применение запрещено.** Всякое интересное определение —
        «прочитать и записать», второй проход молча удвоил бы эффект;
      - **битый скрипт стоит своего актёра, не файла и не игры.** Как битый спрайт в
        загрузчике контента.

      Что осталось: собственные состояния и переходы, реакция на события (урон,
      попадание). Конвертер DECORATE → SharpScript сделан — см. пункт о DECORATE выше.
      «На лету» — это и есть этот интерпретатор, компиляции нет и не будет.
- [x] **Проброс порта через UPnP.** `-upnp` у хоста: найти шлюз по SSDP, разобрать
      описание устройства, добавить правило SOAP-запросом, напечатать внешний адрес,
      снять правило при выходе. Описано в `docs/NETWORK.md`.

      `tools/test-upnp.ps1` (живой запуск, ограниченное время ожидания).

      **Сделано своими сокетами, не через COM.** `refs/NATUPNPLib` — декомпилированный
      interop из `TerrariaServer.exe` (в файлах так и написано: «Decompiled with
      JetBrains decompiler»), то есть чужой код с чужой лицензией — брать нельзя.
      Независимо от лицензии, COM-путь тянет `CustomMarshalers.dll` рядом с exe, а
      проект поставляется одной сборкой. SSDP — это один UDP-датаграмм, SOAP — один
      HTTP POST, и оба на сокетах занимают двести строк без единой зависимости.

      Что выяснилось по дороге и записано в код:

      - **все цели поиска отправляются разом, одно окно ожидания.** Очевидная
        реализация спрашивает их по очереди, и на сети без шлюза это девять секунд на
        каждом запуске (три цели по три секунды). Три датаграммы — это три пакета;
        вместе они дают ту же информацию за треть времени. 9.7 с → 3.6 с на замере;
      - **закрывающий тег ищется по локальному имени**, а не как первый `</`: внутри
        `<service>` первый закрывающий тег принадлежит `<serviceType>`, и «наивная»
        версия обрезала блок на одной строке. Это и был баг, который нашли тесты;
      - **имя тега сравнивается от начала, а не по вхождению**: `<serviceList>`
        совпадал с `service`, потому что пробел после `>` удовлетворял проверке «имя
        кончилось»;
      - **проброс снимается при выходе** и на рабочем потоке с ожиданием в две
        секунды: игра не должна висеть на закрытии, но и правило не должно остаться в
        роутере — это открытый в интернет порт через неделю после игры;
      - **флаг явный.** Программа, которая молча открывает порт в интернет при первом
        запуске, не спрашивала разрешения.

      лимит.

### 13.1. Мышь при открытой консоли — **сделано**

Настоящая причина оказалась не в консоли. Подавление ввода жило внутри `PumpChat()`, после
раннего выхода «нет сетевого драйвера», — то есть в одиночной игре оно не выставлялось
никогда. В сети работало, поэтому и не всплывало. Теперь это отдельный
`UpdateInputSuppression`, вызываемый каждый кадр, а накопленное движение мыши
выбрасывается, а не копится: иначе при закрытии консоли вид прыгает на всё, что рука
успела проехать. Заодно вид больше не наклоняется, пока игра на паузе.
Проверка — `InputSuppressionTest` (3), и один из них специально про одиночную игру.

### 13.2. Прыжок — **сделано**

Клавиша `F` по умолчанию, переназначается в «Опции → Ввод → Клавиши». Восемь единиц
момента за тик против гравитации движка (`Fixed.One` за тик) даёт подъём около тридцати
единиц: хватает на ящик или низкий уступ, не хватает, чтобы покинуть карту или перескочить
лифт. Импульс **ставится**, а не прибавляется — иначе высота зависела бы от того, сколько
игрок простоял, а демо честно записало бы эту разницу и второй игрок её никогда бы не
повторил.

**Решение про формат демо, которое этот пункт блокировало.** Прыжок живёт в
`TicCmd.Jump`, а не в бите `Buttons`: бит 64 отдан метке «игрок ушёл» (13.7), и ей он
нужен в сети. Демо получило вторую версию:

| Версия | Запись | Когда пишется |
|---|---|---|
| 109 | 4 байта на игрока за тик (ванильная) | если за запись никто не прыгал |
| 110 | 5 байт, лишний — прыжок | если прыжок был |

Версия выбирается **при сохранении**, а не при старте записи: буфер всегда пишется
пятибайтовыми записями, а при `Save` либо уплотняется до ванильной, либо остаётся
пятибайтовой. Это не оптимизация, а сохранение двух свойств сразу — демо без прыжка
по-прежнему играется в других портах и совпадает с записями, на которые опираются эталоны
хешей Managed Doom. Безусловная запись версии 110 стоила бы обоих и не дала бы ничего.

**Симуляция без прыжка не изменилась**, и это проверено отдельно: все эталоны хешей
Managed Doom остались валидными, ни один геймплейный тест не тронут. `JumpTest` (6) в том
числе сравнивает два прогона одинакового ввода и требует совпадения хешей.

Сеть: `NetTic` получил одиннадцатый байт в конце записи. Первые десять не сдвинулись,
поэтому старый пир читает тик правильно и просто не умеет прыгать; обе стороны проверяют
длину перед чтением хвоста, и версия протокола не понадобилась.

**Побочно найденный дефект:** `-record` писал демо из одного тика. `StopRecording`
вызывался по первому `NeedWipe`, а мир просит вайп на своём **первом** тике — то есть
запись обрывалась на старте уровня. В headless она не сохранялась вообще: там выход из
цикла, а не `Quit`. Теперь вайп на первом тике запись не закрывает, а headless сохраняет
её явно. Проверка — `tools/test-jump.ps1`: 60 тиков записываются как версия 109 и ровно
240 байт записей.
### 13.3. CRC32 + соль для паролей — **отклонено**

CRC32 (и его вариант JAMCRC, который просто без финального XOR) — **не шифрование и не
хеш для паролей**. Это контрольная сумма: 32 бита, линейная над GF(2). Из неё восстанавливают
вход не перебором, а решением системы уравнений — и это не «сложно», это несколько строк.
Соль помогает только против заранее посчитанных таблиц и ничего не добавляет к стойкости:
у CRC32 её просто нет.

Хуже другое: соль и хеш не решают главную проблему, которая у пароля здесь есть. По
`docs/NETWORK.md` пароль идёт **открытым текстом** в `HELLO`, поэтому наблюдатель видит его
целиком, независимо от того, что делает хост на своей стороне. Хеш на проводе не защищает
от того, кто читает провод.

Что уже сделано и почему это правильный минимум: SHA-256 от обеих сторон и сравнение
дайджестов **без досрочного выхода** — иначе пароль подбирается по времени ответа
посимвольно (`ServerPasswordTest`).

Что действительно дало бы выигрыш, если понадобится:

1. **challenge-response**: хост присылает случайный `nonce`, клиент отвечает
   `HMAC-SHA256(пароль, nonce)`. Пароль перестаёт ходить по проводу, и повтор записанного
   ответа не проходит. Это замена поля в `HELLO`, то есть правка протокола;
2. **медленный KDF** вместо SHA-256 — но он защищает от офлайн-подбора по украденному
   хешу, а хеша у нас никто не хранит: сверка идёт в памяти хоста. То есть выигрыш близок к
   нулю, а стоимость — реальная (PBKDF2 на 100k итераций — это секунды на XP).

Вывод: CRC32 не брать ни в каком виде; при желании усилить — делать challenge-response, и
только вместе с правкой протокола.

### 13.4. ROFL MODE: Konami-код, зеркальный вид, клоуны — **сделано наполовину**

Включается кодом Konami (↑↑↓↓←→←→BA) **в любом меню**, не только на странице System:
пасхалку находят, стуча по стрелкам от скуки, а не прочитав документацию. Подсказок нет.
При включении и выключении пишется ROFL MODE ENABLED / ROFL MODE DISABLED — секрет,
о котором нельзя догадаться, что его нашли, это готовый баг-репорт. Как выключить, не
подсказывается: это и есть игра. 1 апреля включается сам, но **только если игрок ни разу
не выбирал**: режим, который включается каждое 1 апреля против воли владельца машины, —
это уже не пасхалка.

**Зеркалится вид, а не карта.** Это главное решение пункта, и оно про честность цены:

- настоящее зеркало геометрии — это вершины **и** узлы BSP, блокмап и текстурные смещения
  сегментов, все четыре читаются из WAD и обязаны остаться согласованными. Ошибка в любом
  даёт стену наизнанку или растянутую текстуру. Много тонкой геометрии ради шутки;
- зеркало готового кадра даёт то же ощущение — коридор, уходивший вправо, уходит влево — и
  при этом **мир не трогается вообще**. Хеш мира совпадает побитово, демо, записанное с
  режимом, воспроизводится точно, и lockstep про режим не знает.

Цена названа прямо: автомап пришлось зеркалить отдельно, чтобы он не противоречил виду, а
два игрока в сети могут расходиться во мнении, где у коридора левая сторона, если режим
включён у одного. Для шутки, которой никто не обязан пользоваться, это приемлемо.

**Ввод инвертируется** (поворот и стрейф) **до** сборки команды: зеркальная картинка с
обычным управлением читается как поломка, а не как шутка — жмёшь влево, вид уходит вправо.
Так как инверсия происходит до команды, демо записывает уже инвертированную команду и
воспроизводится без всякого знания о режиме.

Что далось дорого и записано, чтобы не повторять:

- **буфер кадра столбцовый** (x * height + y), а не строчный: рендерер рисует столбцами.
  Первая версия MirrorRect читала его как строки, и картинка получалась почти-зеркалом —
  достаточно похожей, чтобы тест «зеркало самого себя» проходил, и достаточно неправильной,
  чтобы игрок видел мусор. Тест на ось (пиксель переезжает в зеркальный **столбец** того же
  ряда) появился именно после этого;
- **BMP пишется снизу вверх** (iHeight положительный). Тест, читавший его сверху вниз,
  проверял зеркальность строки статуса и неизменность вида — ровно наоборот, — и обвинял
  исправный рендерер.

**Не сделано: «Приколисты».** Проверено по efs/Doom2D: «Prikol» там — **Prikol Software**,
студия, а не персонаж. Уникальные спрайты у Doom2D есть (MANF, ROBO, FISH), но
человекоподобного «Приколиста» в них нет. Значит подмена монстров упирается не в код, а в
**графику**: нужны кадры персонажа, рисовать их некому. Механизм подмены при этом готов —
замена актора по DoomEdNum работает и в DECORATE, и в SharpScript.

Проверка: KonamiCodeTest (8), RoflModeTest (10), 	ools/test-rofl.ps1 — живой прогон,
где вид зеркалён на 100%, строка статуса не тронута, а хеш мира совпадает с прогоном без
режима.
### 13.5. Зависание, когда фаервол блокирует сеть — **сделано**

Три причины, и все три — про то, что игра врала о своём состоянии:

- **окно закрыли во время рукопожатия.** Рукопожатие идёт в отдельном потоке, а главный
  крутит сообщения и не смотрел, жив ли ещё окно. Хост, ждущий гостя, жил после закрытия
  окна все пять минут ожидания. Теперь — 0.2 с;
- **ожидание клавиши на выходе** держало процесс открытым. Лаунчер ждёт завершения
  процесса, поэтому показывал «игра запущена» после закрытия окна, а закрытие консоли
  выглядело как падение. Лаунчер теперь помечает запущенный процесс, и помеченный не
  ждёт клавишу; непомеченный ждёт, но 15 секунд, а не вечно;
- **сообщение об ошибке** в этом ожидании и было тем, что игрок читал как «повисло».

Чего это не лечит и почему: сам диалог фаервола рисует Windows, и сокет, созданный до
появления правила, может остаться заблокированным — отсюда «после разрешения помогает
только перезапуск». Это поведение ОС; наша часть — не висеть и сказать правду.

### 13.6. Консоль остаётся после закрытия окна — **сделано**

Тот же корень, что 13.5: ожидание клавиши на выходе. Лаунчер видит процесс живым, пока
это ожидание не закончится.

### 13.7. Тело отключившегося игрока остаётся — **сделано**

Слот убрать нельзя: мир на трёх и мир на двух — разные миры, поэтому слот остаётся
инертным и хост шлёт за него пустые команды. Но **тело** стояло посреди карты живым, и это
то, что видел игрок.

Убрать его можно только детерминированно, а детерминированно — значит через поток команд:
если каждая сторона уберёт тело «когда узнала», они разойдутся. Поэтому появился бит
`TicCmdButtons.Gone` (64), который хост ставит в пустых командах отданного слота, а
`DoomGame.DepartedPlayers` по нему убивает тело. Бит едет в команде, значит применяется на
одном и том же тике на всех концах; локальный ввод его не ставит никогда, поэтому в демо он
попасть не может.

Тело именно **убивается**, а не исчезает, и это выбор, а не компромисс:

- труп инертен и не перекрывает проход — это и была жалоба;
- `PlayersInGame()` продолжает считать слот, поэтому оставшийся игрок в коопе после смерти
  возрождается, а не перезапускает уровень (сброс `InGame` дал бы именно это);
- никому не надо учиться терпеть игрока без тела: строка статуса, интермиссия и обработка
  смерти работают как раньше.

Бит 64 — единственный свободный в `Buttons`, и он же был нужен прыжку (13.2). Отдан этому
пункту, потому что прыжок всё равно требует решения про формат демо: он обязан ехать в
`TicCmd`, а «сеть только» метке формат демо не нужен.

Проверка: `DepartedPlayerTest` (3) и `tools/test-net-leave.ps1` — в нём уход игрока
происходит по-настоящему, и хеши мира хоста и гостя на тике 700 совпадают, то есть труп
появляется на одном тике у обоих.

### 13.8. Все акторы в SharpScript, распаковка в `dptdoom-data` — **сделано**

Идея правильная и это то, куда проект идёт: в ZDoom/GZDoom нативные акторы тоже описаны
в `zdoom.pk3`, а не зашиты в код, и именно поэтому там можно собрать свою игру.

**Сделано: встроенная таблица актёров — это текст на диске.** При первом запуске игра
выкладывает её как SharpScript — `dptdoom-data/actors/{monsters,items,decorations}.dpts`
плюс README. 118 из 137 актёров; остальные 19 без номера на карте (игрок, трассеры,
вспышки), а язык называет актёра по номеру.

Ценность не в аккуратности, а в том, что вопрос «какая у дробовичника вероятность боли»
раньше не имел ответа, не требующего читать исходники движка.

**Папка загружается, и загружается до DeHackEd.** Это второй шаг и он важнее первого:
текст, который только лежит рядом, — справочник; текст, который применяется, — источник
истины. Три следствия, и все проверены:

- правишь число в файле — игра меняется, пересобирать нечего;
- `.deh`-патч, загруженный рядом, всё равно главнее: он применяется после;
- удалил папку — вернулись встроенные значения.

Порядок здесь не деталь, а весь смысл. Скрипты вообще применяются **после** DeHackEd (мод
может читать результат патча), поэтому текст, применённый в общем порядке, выставил бы все
поля обратно и молча отменил патч. Отсюда две фазы: папка — до, скрипты мода — после.
Проверка порядка — в исходнике (`TheFolderIsLoadedBeforeDeHackEd`), потому что
поведенческий тест прошёл бы и при совпадении значений.

Три решения по ходу:

- **три файла, а не сто восемнадцать.** Сто восемнадцать файлов по две функции в каждом
  искать труднее, чем три файла с заголовком на актёра;
- **никогда не перезаписывать.** Смысл распаковки в том, что её правят; второй запуск,
  затирающий правку, сделал бы функцию ловушкой;
- **`-nodata`** — ни читать, ни писать. Прогон, который пишет файлы, пишет на машину, а
  тест, оставляющий артефакты, приходится чистить руками.

**Отпечаток сборки.** README несёт отпечаток таблицы, которая файлы написала. Если он не
совпадает с текущей, игра говорит об этом при старте: значения могли устареть. Не ошибка —
держать старый справочник это выбор, — но молчать нельзя. Отпечаток считается **до**
применения папки; посчитанный после, он сравнивал бы папку саму с собой, и любая правка
объявляла бы её устаревшей (на этом я и попался).

Составные флаги (`Translation` — двухбитное поле в одежде флага) генератор пропускает:
`Flag` их отвергает, потому что это не степень двойки.

**Ловушка, которую пришлось закрыть в тестах.** Таблица актёров статическая, и папка
меняет её. Значит тест, меняющий актёра, оставляет изменение всем последующим — и падение
всплывает в чужом файле. В проекте это уже случалось (тест выставил импу 400 здоровья и
сломал сравнение хешей демо через три файла). Появился `ActorTableSnapshot`: снимок и
восстановление всех полей.

**Что осталось, и это уже про независимость от Doom:**

1. **убрать таблицу из кода** — сейчас она остаётся запасным вариантом, когда папки нет.
   Пока она есть, «всё в тексте» верно лишь наполовину: сборка без папки ведёт себя
   по-старому;
2. **остальные форматы** — `ANIMDEFS`, `LOCKDEFS`, `TERRAIN`. **MAPINFO и SNDINFO уже
   сделаны** — см. `docs/MAPINFO.md`, `docs/SNDINFO.md` и пункты ниже;
3. **и только потом** «своя игра с нуля».

Стена, которую видно уже сейчас: `DoomInfo.MobjInfos` индексируется перечислением
`MobjType`, а текст не может создать элемент перечисления. То есть **типы остаются в
коде**, в тексте — их свойства и состояния. Это ровно та граница, которую в ZDoom решают
отдельным реестром классов; у нас для неё есть резерв `DoomInfo.CustomActorReserve`, но он
на 32 записи.

Проверка: `ActorTemplateTest` (6), `ActorFolderTest` (5, включая порядок относительно
DeHackEd и устаревший отпечаток), `tools/test-actors.ps1` (живой прогон: правка файла
меняет хеш мира).
### 13.9. MAPINFO: название, небо и музыка уровней — **сделано**

Первый из «остальных форматов» после актёров. Описано в `docs/MAPINFO.md`.

Поднабор выбран по тому же правилу, что и у DECORATE: то, без чего карта выглядит
сломанной. Три свойства — **название** (автомап и интермиссия пишут имя уровня, а на чужой
карте пишут «entryway»), **небо** (карта ночью с ванильным небом выглядит незаконченной) и
**музыка** (своя дорожка — первое, что мод кладёт в файл, и последнее, что движок сыграл бы).

Лампа `MAPINFO` внутри PWAD — основной способ, ключ `-mapinfo` — для правки файла без
пересборки. Всё, что не поддерживается (`cluster`, `defaultmap`, `fogdensity`, флаги
уровня), **называется в отчёте** и игнорируется: парсер, молча принимающий то, чего не
умеет, даёт мод, который выглядит поддерживаемым и не является.

Три вещи, которые выяснились по дороге:

- **`textures[name]` бросает `KeyNotFoundException`, а не возвращает null.** Проверка на
  null после индексатора не выполняется никогда, и опечатка в имени неба роняла бы весь
  уровень. Правильный вопрос — `GetNumber(name) >= 0`;
- **имена лампов в WAD дополняются нулями, а не пробелами.** Мой тест писал
  `"MAPINFO "` (с пробелом), читатель останавливается на первом нуле — и лампа не
  находилась. Это же делает и ванильный Doom, так что строгость верная; в
  `tools/test-decorate.ps1` та же ошибка не всплыла только потому, что «DECORATE» — ровно
  восемь символов;
- **название уровня нигде не печаталось.** Строка была `map MAP01: OK (loaded)` — слово,
  которое уже сказано словом `OK`. Теперь там имя: `map MAP01: OK (level 1: entryway)`.
  Это и полезно (в логе появилось единственное, чего в нём не хватало), и необходимо:
  название, видимое только на автомапе, нельзя проверить headless-прогоном, и MAPINFO
  проверялся бы лишь юнит-тестом на структуру, без связи с картой.

Музыка потребовала перегрузки `IMusic.StartMusic(string lumpName, ...)`: дорожка мода —
это `D_MYSONG`, которого в перечислении `Bgm` нет и быть не может. Префикс `D_`
дописывается, если его нет, потому что в файлах встречаются оба написания.

Проверка: `MapInfoTest` (14), `MapInfoAppliedTest` (5, включая лампу в PWAD и
несуществующее небо), `tools/test-mapinfo.ps1`.
### 13.10. SNDINFO: какой люмп играет звук по имени — **сделано**

Второй формат после MAPINFO. Описано в `docs/SNDINFO.md`.

Движок находил люмп звука по соглашению — `DS` плюс имя, — что работает для IWAD и ломается на
первом звуке мода, названном иначе. SNDINFO ломает соглашение тремя формами: `имя люмп`,
`$alias новое старое` и `$random имя { люмпы }`.

Имена — это **имена `Sfx` движка**, потому что звук выбирается перечислением, а перечисление не
растёт в рантайме. Та же стена, что у `MobjType`, и тот же ответ: тип в коде, данные в тексте.
Практический смысл всё равно большой: мод может дать **ванильному** звуку свою запись без
единой строки кода.

Два решения, которые легко было принять неправильно:

- **вариант `$random` выбирается обычным `Random`, не генератором движка.** Какой шаг прозвучал
  — это подача, а не симуляция; взять его из мирового генератора значило бы сдвинуть мир на
  одно число и положить выбор звука в хеш. Один вариант генератор не трогает вовсе, так что мод
  без `$random` не платит ничего;
- **приоритет канала берётся по самому громкому варианту**, а не по первому. Приоритет
  сравнивается с другими звуками за канал, и тихий вариант громкого звука не должен проигрывать
  эти сравнения за весь звук.

Цикл алиасов (`$alias a b` и `$alias b a`) разрешается в «ничего» после восьми шагов: без
предела глубины это было бы зависание внутри кадра, то есть зависание с нарисованным окном.

`-soundtest` резолвит имя через SNDINFO так же, как игра, и печатает `DSDOROPN -> DSDORCLS`,
когда файл так сказал. Инструмент, который игнорировал бы маппинг, рендерил бы люмп, которого
игра не играет, и врал бы о единственном, что должен отвечать.

Проверка: `SoundInfoTest` (15), `tools/test-sndinfo.ps1` (живой прогон: имя играет указанный
люмп, алиас разрешается, неподдерживаемая директива названа, отсутствующий люмп назван).
## Известные ограничения

- Windows XP не проверен на живой машине.
- Сеть не Internet-ready: нет шифрования и аккаунтов. Relay снимает проблему
  проброса порта, но трафик идёт через master открытым текстом.

- P2P-загрузка ресурсов не реализована.
